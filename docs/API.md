# API

The backend serves JSON under `/api`, images under `/media`, and the built web
page for every other path. All errors are `{"detail": "a sentence the owner can
read"}` with a matching status code. Everything except `health`, `session`,
`setup` and `login` needs the session cookie (set by `setup` or `login`,
HttpOnly, SameSite=Strict); without it the answer is 401.

## Session
| Call | Result |
|---|---|
| `GET /api/health` | `{app:"closet", status:"ok", version, model_state, setup_required, profile}` |
| `GET /api/session` | `{authenticated, setup_required, version, profile}` |
| `POST /api/setup {passphrase}` | 204 and logs in. 422 if shorter than 8 characters, 409 if already set. |
| `POST /api/login {passphrase}` | 204. 401 if wrong; 429 with `Retry-After` after 5 wrong tries in 5 minutes. |
| `POST /api/logout` | 204 |

## Items
`ItemSummary`: `id, name, category, color, color_hex, pattern, location, rating, status, cutout_state, tag_state, thumb_url, has_illustration, illustration_url, has_photo, last_worn, wear_count, wears_since_wash, laundry, created_at, updated_at`.
`last_worn` is the date of the latest wear (`YYYY-MM-DD`) or null; `wear_count` counts every wear; `wears_since_wash` counts wears recorded since the item was last marked clean; `laundry` is `clean` or `laundry`. `location` says where the item lives when it is clean (`closet`, `drawer` or `storage`); being in the wash is `laundry`, not a location.
`illustration_url` (or null) is an SVG image address that changes whenever the drawing changes, so it can be used in an `<img>` and cached forever.
Every item gets its drawing: from its stored answer when there is one, otherwise from `category, color_hex, pattern, silhouette`; where the owner has set a field (`source[field] == "user"`) the drawing follows the item's field, not the answer. It is made again when describing finishes, when a `PATCH` changes `category, color, color_hex, pattern` or `silhouette`, and, when the drawing code is newer than the stored drawing, the first time the item is listed or opened. A bag, belt, hat, scarf, "other" or an item with no category has no drawing (`illustration_url` null). Drawing never fails an item: an answer the templates cannot draw gives the plainest drawing of its category.
`cutout_state` is `none` (no photo), `pending`, `processing`, `ready` or `failed`. `tag_state` is how far Claude has got describing the item: `none` (never asked: no photo or cutout yet, the demo closet's own uploads, or items added before tagging existed), `waiting` (queued; also while no route to Claude can be used), `working`, `done` or `failed`. `thumb_url` is the cutout thumbnail once ready, the photo thumbnail before that, or null.

`Item` is the summary plus `formality, season, brand, size, material, fit_notes, condition, price_cents, acquired_on, notes, rating_reason, illustration_svg, cutout_error, silhouette{}, confidence{}, source{}, photos[], recent_wears[]` (the 10 latest wear dates, newest first), and for tagging `tag_error` (why it failed, in plain words, or null; while the item waits for the API key's monthly limit, or because Anthropic turns down how Claude Code is signed in, it says so, and it is cleared when the item goes ahead), `tag_route` (`plan`, `api`, or `demo` for the demo closet's answers made in advance), `tag_model`, `tag_schema_version`, `tagged_at`, `details` (the construction details of the stored answer, taxonomy values, without `other_features`; null before an answer) `seen_not_drawn[]` (the answer's `other_features`: what Claude saw that the drawing does not show) and `drawing_notes[]` (what the drawing itself could not show, in plain words: a pattern drawn as its colour only, a detail drawn approximately, details it does not know, or that it was drawn plain; empty for the demo closet's drawings). `pattern_state` is how far measuring the item's pattern from its photo has got (or, for a top with a graphic, lifting its print): null (plain, nothing to measure), `waiting`, `working` (a minute or two on a large photo), `done` (the drawing shows the pattern or the print) or `failed`, with `pattern_error` saying why in plain words; a failed or waiting item is drawn in its colour and `drawing_notes` says so. `pattern_colors[]` are the colours measured from the pattern, largest first, each `{color, hex, share}` (`share` 0..1); empty until it is measured, and the item's `color` is then the main one unless the owner set it. `failure` is null unless the cutout or the description has failed for good; then it is `{stage: "cutout"|"description", reason, details}`: `reason` is the plain sentence the item shows (the same as `cutout_error` or `tag_error`), and `details` is the reason the failed job recorded, at most 500 characters, with anything shaped like a key or a token (`sk-…`, `api_key=…`, `Bearer …`, `Authorization: …`, long mixes of letters and digits), e-mail addresses and file paths outside Closet's data folder replaced by `[hidden]` or `[a path outside Closet]`; a path inside the data folder starts with `[Closet folder]`. `details` is null when nothing was recorded. The cutout comes first when both failed. The same cleaned reason is written once to the log, at WARNING with the item's id, when the item is marked failed. `own_details{}` holds the details the owner set (see `GET /api/items/{id}/details`); they are laid over the answer's `details` when the item is drawn, and "Describe it again" leaves them as they are.

Once an item's cutout is ready it is queued for Claude in the same queue as cutouts (a `tag` job): three attempts, then `failed`; while no route can be used it waits without using an attempt. The whole answer is stored with the item. It fills `name` (only when there is none), `category, color, color_hex, pattern, formality, season, silhouette, material`, sets `source[field] = "ai"` and `confidence[field]` (plus `confidence.details`), and never changes a field the owner has set: `source[field] == "user"`, or a value that was not filled by an earlier answer (a name given at upload). A `PATCH` marks each field it sets as the owner's.
Each photo: `id, kind, url, thumb_url, cutout_url, cutout_thumb_url, width, height` (`cutout_*` are null until ready).

| Call | Result |
|---|---|
| `GET /api/vocab` | Allowed values: `category, color, pattern, formality, season, location, condition, rating` (lists) and `silhouette` (object of lists). |
| `GET /api/items?status=active\|archived&category=&q=&laundry=clean\|laundry` | `{items: [ItemSummary]}`, newest first. |
| `POST /api/items` multipart: `photo` (file), `client_key`, optional `name`, optional `photo_sha256` | 201 `Item` with `cutout_state: "pending"` and `duplicate: false`. Sending the same `client_key` again returns the first item with 200 and `duplicate: false`, so retries never duplicate. A photo already in the closet (an active or archived item, not a deleted one) is not added again: 200 with the existing item and `duplicate: true`. "The same photo" is decided by `photo_sha256`, the SHA-256 (64 hex characters) of the file as the owner chose it, before the page shrank it; without it, the hash of the bytes received. 422 if `photo_sha256` is malformed, 400 if the file is not a readable photo. |
| `GET /api/items/{id}` | `Item` |
| `PATCH /api/items/{id}` JSON of fields to change | `Item`. Changeable: `name, category, color, color_hex, pattern, formality, season, location, condition, rating, rating_reason, brand, size, material, fit_notes, acquired_on, notes, price_cents, status, silhouette` (silhouette is merged; a null value removes a key). 422 with a readable message for a value outside the vocabulary (including `location: "laundry"`; use the laundry call instead). |
| `DELETE /api/items/{id}` | 204; the item and its images are removed. |
| `POST /api/items/{id}/retry-cutout` | Try the cutout again: 202 `Item` with `cutout_state: "pending"`. Never queues a second job: unchanged if the cutout is already waiting or being made. |
| `POST /api/items/{id}/retag` | Ask Claude to describe the item again: 202 `Item` with `tag_state: "waiting"` (unchanged if it is already waiting or being described, or if the cutout is still being made, since describing follows it). 409 with a plain sentence when the item has no photo, its cutout failed, or the demo closet is open (it is never sent to Claude). |
| `GET /api/review` | The review queue: `{count, items: [ReviewItem], waiting, failed, waiting_items, failed_items}`. `items` are the active items with at least one doubtful field, most doubtful first (lowest confidence, then more doubtful fields, then newest). A field is doubtful when the tagger filled it (`source` is `ai`, or `demo` in the demo closet), it has a value, and its confidence is below that field's threshold (`UNSURE_BELOW` in `closet/review.py`). `ReviewItem` is an `ItemSummary` plus `picture_url` and `picture_kind` (`cutout`, `photo` or `illustration`; the largest picture there is) and `fields: [{field, value, confidence, allowed}]`, only the doubtful ones, in the order category, colour, pattern, formality, season, silhouette. For `silhouette`, `value` is the whole silhouette object and `allowed` the allowed values of each key it has. `count` is the number of `items`. Items still waiting to be described (or, in the main closet, whose cutout is still being made before describing) and items whose describing failed are never in `items`: `waiting` and `failed` count them and `waiting_items`/`failed_items` list them as `ItemSummary`. Archived items are left out. |
| `POST /api/items/{id}/confirm {fields: [field]}` | Marks the listed fields as the owner's without changing their values (`source` becomes `user`, confidence 1), so they never come back to the queue, also after "Describe it again". Fields: `category, color, pattern, formality, season, silhouette`. 200 `Item`; 422 for an empty list or an unknown field; 404 if there is no such item. Changing a value uses `PATCH /api/items/{id}`, which marks it as the owner's too. Skipping an item needs no call. |
| `GET /api/items/{id}/details` | What can be fixed on this kind of garment: `{kind: "top"\|"bottom"\|"shoe"\|null, groups: [{id, title, details: [{name, title, value, words, own}]}], message}`. Groups, in order: `neck` (Collar and neck), `front`, `sleeves` (Sleeves and cuffs), `pockets`, `hem`, `sole` (Sole and laces), `shape`, `cloth`, each only where it applies. `name` is a field of the tagging schema's `Details`, or a feature (`v_insert`, `toe_cap` ...) set `"yes"` or `"no"`; `value` is the value drawn now; `words` and `title` are plain words; `own` is true when the owner set it. `kind` null (a bag, a belt, nothing known yet) comes with a `message` and no groups. |
| `GET /api/items/{id}/details/{name}` | The choices for one detail: `{name, title, value, words, own, choices: [{value, words, current, svg}]}`, in the schema's order (`placket_buttons`: 0 to 10). `svg` is a small drawing of the item with that value, made by the drawing code, and is given only where it differs from the drawing with the current value (null for the current value and for values that look the same). 404 if the detail is not one for this kind of garment. |
| `PUT /api/items/{id}/details {details: {name: value\|null}}` | Sets one or several of the owner's details: 200 `Item`, drawn again. `null` gives a detail back to Claude's answer. 422 (nothing changed) for a value not among the choices or a detail not for this kind of garment. |
| `POST /api/items/{id}/correct {sentence}` | Asks Claude what a sentence ("it has three buttons", "the collar is white") changes; nothing is applied. `{state, changes: [{name, title, value, before, before_words, after_words}], not_understood, sent, sentence, message, limit}`. `state`: `understood` (changes to confirm), `not_understood` (no change; `not_understood` says what, also for values outside the vocabulary, which are never kept), `waiting` (no route to Claude can be used now; `message`; `limit` is true when only this month's spending limit for the API key stood in the way, and the message offers the picker instead), `failed` (Claude gave no usable answer; `message`). `name` is a detail, one of `category, color, pattern, formality, season`, or `silhouette.<part>`. Claude is sent the sentence, the item's description (its fields and details, not its name, notes or brand) and the allowed values; the photo (the front cutout) only when the sentence cannot be understood without it and its background has been removed (otherwise no photo is sent and `not_understood` says why), and `sent` says which. Same routes as tagging: the plan first, the API key only when switched on; every call is in the record of calls (`GET /api/tagging/spend`) with purpose `correct_item`, and every API request is checked against the monthly limit before it is made. 422 for an empty sentence or one over 500 characters. 409 in the demo closet, which is never sent to Claude. |
| `POST /api/items/{id}/correct/confirm {sentence, changes: [{name, value, before?}]}` | Applies the confirmed changes as one change in the history: 200 `Item`, drawn again. Fields are set as the owner's (`source` `user`; a colour also sets `color_hex`); details become the owner's. 422 (nothing changed) for any value outside the vocabulary. 409 when a change's `before` (the value Claude read) is no longer the item's, and in the demo closet. |
| `GET /api/items/{id}/history` | Every change to the item's description, newest first: `[{id, at, by: "owner"\|"claude", kind: "answer"\|"field"\|"detail"\|"sentence"\|"undo", sentence, undoes, undone, can_undo, why_not, first_description, parts: [{target: "field"\|"detail"\|"answer", name, title, before, after, before_words, after_words, same}]}]`. Recorded: Claude's answer arriving (`answer`, also when it says the same again), a `PATCH` that changes `name, category, color, color_hex, pattern, formality, season, silhouette` or `material`, or makes one of them the owner's by giving the same value (`field`), confirming fields from the review queue (`field`; `same` is true when only who set it changed), details picked (`detail`), a confirmed correction by sentence (`sentence`), and undoing (`undo`). For `silhouette`, `before` and `after` hold only the parts that changed. Changing the kind of garment drops the owner's details the new kind does not have, in the same entry. |
| `POST /api/items/{id}/history/{change_id}/undo` | Puts back what that change replaced (values, who set them, the owner's details, Claude's earlier answer and how sure it was) and draws the item again (or puts back the drawing the item had when it was last exactly so, which keeps the demo closet's drawings made in advance): `{item: Item, history}`; the undo is itself a change that can be undone. 409 with a plain sentence when the change was already undone, when a later change touched the same field or detail ("undo that first"), or for Claude's first description; a later change that was itself undone does not block. A field given back to the tagger is what Claude's current answer says. 404 if the change is not in this item's history. |
| `GET /api/items/{id}/wears` | `{wears: [{worn_on, created_at}]}`, newest first. |
| `POST /api/items/{id}/wears {worn_on?}` | Records a wear. `worn_on` is `YYYY-MM-DD` and defaults to today in the computer's local date. 201 `Item`; 200 `Item` if that day was already recorded (one wear per item per day). 422 for a date in the future or not in that form. |
| `DELETE /api/items/{id}/wears/{YYYY-MM-DD}` | 200 `Item`. 404 if there is no wear on that day. |
| `POST /api/wears {item_ids, worn_on?}` | Records a wear for several items at once (an outfit), in one go: all of them or none. `item_ids` is 1 to 20 item ids; `worn_on` as above. Items already worn that day are left as they are. `{worn_on, recorded, items}`: `recorded` lists the ids whose wear is new (only these should be removed to undo), `items` is the `ItemSummary` of every item asked for, in the same order. 201 if any wear was new, else 200. 404 if an item does not exist, 422 for a bad date or list. |
| `POST /api/wears/remove {item_ids, worn_on}` | Undoes `POST /api/wears`: removes each item's wear on that day, all or none. Items with no wear that day are skipped. `{worn_on, removed, items}`. 404 if an item does not exist, 422 for a bad date or list. |
| `POST /api/wears {item_ids, worn_on?, outfit}` | With `outfit {pieces, context?, score?, reasons?, warnings?}` the wears are recorded together with a worn outfit, in one go. `pieces` is the outfit by place as `POST /api/outfits/today` gives it and must hold exactly `item_ids`; `context {low_c, high_c, rain, occasion, mood}` is the day it was offered for; `score` 0 to 100; `reasons` and `warnings` lists of sentences (more than 30 are cut to 30, a sentence over 500 characters is shortened to end in "…"). The same pieces recorded again on the same day (from another device, say) give back the outfit already there. The answer has `outfit` (a `WornOutfit`, below) as well. 422 on a bad outfit, and then nothing is recorded. |
| `POST /api/wears/remove {item_ids, worn_on, outfit_id}` | With `outfit_id` the outfit is removed with the wears it recorded, whichever device recorded them (`item_ids` may then be empty); a wear another outfit that day also holds is kept and handed on to that outfit. If the outfit was removed already, only the wears in `item_ids` that no outfit that day holds go. The answer has `outfit_removed` (true or false) as well. |
| `POST /api/items/{id}/laundry {state: "laundry"\|"clean"}` | 200 `Item`. Marking an item clean sets `wears_since_wash` to 0 (also when it was already clean: it has just been washed). |
| `GET /api/items/{id}/illustration.svg` | The item's drawing as `image/svg+xml` (made again first if the drawing code is newer); 404 if it has none. |
| `GET /media/{path}` | A WebP image; cacheable forever (paths never change content). |

## Outfits
| Call | Result |
|---|---|
| `POST /api/outfits/suggest {low_c, high_c, rain?, occasion?, mood?, build_around?, leave_out?, worn_days_ago?, count?}` | Today's outfits from the open closet, chosen by rule (`backend/closet/outfits.py`). `low_c` and `high_c` are the day's low and high in °C; `rain` true or false (default false); `occasion` one of the formality values (default `casual`); `mood` `usual`, `sharp` or `relaxed` (default `usual`); `build_around` an item id that must be in every outfit; `leave_out` a list of item ids; `worn_days_ago` an object of item id to days since last worn (0 is today); `count` 1 to 10 (default 3). Answer: `{outfits: [{pieces: {base, mid, outer, bottom, shoes, accessories[]}, score, reasons[], warnings[]}], missing[]}`. `pieces` holds item ids (`mid` and `outer` may be null); `score` is 0 to 100, best first; `reasons` say why the pieces go together and `warnings` what to be aware of, both as sentences. When no outfit can be made `outfits` is empty and `missing` says why ("There are no shoes in this closet yet."). Archived items, items in the laundry and items rated dislike are never used. 422 with a sentence for a bad value or a `build_around` item that is not in the open closet; 400 for a body that is not JSON. |
| `POST /api/outfits/today {occasion?, mood?, build_around?, leave_out?, count?, low_c?, high_c?, rain?}` | Today's outfits with the day filled in: `low_c`, `high_c` and `rain` come from the forecast for the saved place (`GET /api/weather`) unless given, and any one of them that is given wins; how many days ago each item was last worn comes from the wear log; items in the laundry are never used. The other fields are as in `suggest` (`worn_days_ago` is not accepted). Answer: what `suggest` answers plus `context: {date, low_c, high_c, rain, source, old, place, rain_chance, summary, message}`: `source` is `forecast`, `given` or `forecast and given`; `old` is true when the forecast is one kept from before because Open-Meteo could not be reached, and `message` then says so in plain words (as `GET /api/weather` does; null otherwise); `place` is the saved place's name when the forecast was used; `rain_chance` (percent) and `summary` come from the forecast, else null; `date` is the forecast's date, or the computer's date when no forecast was used. With no saved place and no temperatures given (or a forecast that cannot be had), 422 with a sentence asking for one or the other. Other 422 and 400 answers as in `suggest`. |
| `POST /api/outfits/figure {base?, mid?, outer?, bottom?, shoes?}` | The outfit drawn as worn, front view, as one SVG (`image/svg+xml`, not cached): each value is an item id from the open closet, or null for a place left empty; at least one is needed. Each item is drawn from what its own drawing is drawn from (the tagger's description with the owner's corrections, else its category and fields, in its own colour). A place given an item of the wrong kind for it (shoes as the bottom) is not drawn, and an item that cannot be drawn is drawn as the plainest of its kind. Any other key, a value that is not a string or null, or nothing at all: 422; an id not in this closet: 422 naming the place. Not valid JSON: 400. Login required. |
| `POST /api/outfits/today {…, again?}` | `again` is a worn outfit's id: today's outfits start from it, keeping each of its pieces that can be worn today (clean, not archived, not rated dislike, not left out) and filling the places whose piece cannot. `context.again` is then `{id, worn_on, kept, unavailable}` (item ids); without `again` the key is not there. 422 when the outfit is no longer in the list. Rated outfits always shape the answer: see "Learning from ratings" in `docs/DECISIONS.md`. |
| `GET /api/outfits/worn?limit&before` | Worn outfits, newest first: `{outfits: [WornOutfit], next}`. `limit` 1 to 100 (default 20); pass `next` back as `before` for the page after (`next` is null on the last page). `WornOutfit` is `{id, worn_on, recorded_by ("today" or "hand"), pieces {base, mid, outer, bottom, shoes, accessories}, context (null when recorded by hand), score, reasons, warnings, rating, rating_reasons, rating_note, rated_at, created_at, gone}`. `pieces` are the outfit as it was worn, even after a piece is deleted from the closet; `gone` lists those deleted pieces, and such an outfit no longer teaches Today anything. An outfit is removed from the list with the last of its pieces. |
| `POST /api/outfits/worn {item_ids, worn_on?}` | Records an outfit by hand, for a day dressed without the app: 2 or more pieces, put in their places by category (tops layered tee or polo, shirt, sweater or hoodie, jacket, coat; one bottom; one pair of shoes; accessories). Their wears are recorded too (those already there are kept). 201 with the `WornOutfit`; the same pieces on the same day give back the outfit already there. 422 with a sentence when the pieces cannot make an outfit. |
| `PUT /api/outfits/worn/{id}/rating {rating, reasons?, note?}` | Sets, changes or (with `rating: null`) clears a rating. `rating` is `loved`, `fine` or `not_again`; `reasons` any of `too_warm`, `too_cold`, `too_dressy`, `too_casual`, `colours_clashed`, `uncomfortable`, `compliments`, `other`; `note` (up to 300 characters) only with `other`. The `WornOutfit`. 404 when it is not in the open closet. |
| `DELETE /api/outfits/worn/{id}` | Forgets a worn outfit with the wears it recorded (a wear another outfit that day holds is kept and handed on to it; a wear that was there before is kept). 204; 404 when it is not there. |

## Where you are and the weather
Both ask Open-Meteo (no key needed) in a worker thread, through the computer's certificates, and give up after 6 seconds. Only the words searched for and the saved place's coordinates and time zone are sent; nothing about the closet.

| Call | Result |
|---|---|
| `GET /api/places?q=` | Places matching the name, from Open-Meteo's geocoding service: `{places: [{name, latitude, longitude, timezone}]}`, at most 8. `name` reads "Brooklyn, New York, United States". Fewer than 2 letters gives an empty list without asking. 502 with a sentence when the service cannot be reached. |
| `GET /api/weather` | Today's weather for the saved place: `{place, weather, old, is_today, message}`. `weather` is `{date, low_c, high_c, rain_chance, rain, summary, fetched_at}` or null: the day's low and high in °C, the highest chance of rain in percent (null if the forecast has none), `rain` true at 50% or more (or, with no chance given, when the summary is wet), `summary` one word (`clear`, `cloudy`, `foggy`, `drizzle`, `rain`, `snow`, `storms`, or `mixed`), `fetched_at` when it was asked (UTC). A forecast is reused for an hour (and asked again after midnight at the place). When Open-Meteo cannot be reached the last forecast for the same place is returned with `old: true` and a `message`; `is_today` says whether it is for today at the place. With no saved place, or no forecast at all, `weather` is null and `message` says why in plain words; the answer is still 200. |

## What's missing
| Call | Result |
|---|---|
| `GET /api/gaps` | What the open closet is missing, found by rule (`backend/closet/gaps.py`) from its items and wear log. Answer: `{enough, message, gaps: [gap], notes: [{kind, text, items[]}], checked: {items, wears, days}}`. When the closet has fewer than 8 pieces of clothing `enough` is false, `message` says so in a sentence and `gaps` is empty; otherwise `message` is null. Each gap: `{id, name, look_for: {category, formality, season, weight_class, colors[], pattern, material}, why[], score, found_by[], evidence: {days: [{temperature, low_c, high_c, rain, occasion, words}], items[]}}`, best first, at most 8. `name` is in plain words ("A rain-proof outer layer"); `look_for` uses the item fields (null where it does not matter; `material` is a phrase); `why` is sentences naming the owner's items; `score` is 0 to 100; `found_by` is one or more of `days`, `thin_place`, `orphan`, `worn_most`, `basic`; `evidence.items` are item ids of the open closet. `notes` holds things that are not gaps (`never_worn`: items with no wear in the log). Archived items are left out; items in the laundry count as owned. The answer is kept until an item or a wear changes (a wash does not count), so a second call is instant. Each gap also carries the owner's decision on it: `state` is `open`, `hidden` ("Not for me", with `hidden_reason`) or `wished` (on the wishlist, with `wish_id`). Up to 8 open gaps are given, and every hidden or wished one besides, in their places in the order; a decision does not push a new gap off the list. |
| `POST /api/gaps/{id}/hide` | "Not for me": hides the gap. Body `{reason}` (optional): `have_one` (I have one that is not in the closet yet), `never_wear` (I never dress like that), `too_expensive`, `other`. Answer `{gap_id, name, reason, hidden_at}`. 404 when the gap is not in the current analysis; 409 when it is on the wishlist (remove the wish first); 422 for another reason. Hiding again changes the reason. The gap stays hidden when the analysis runs again. |
| `DELETE /api/gaps/{id}/hide` | Brings a hidden gap back. 204; 404 when it is not hidden. |
| `GET /api/wishlist` | What the owner decided to look for, newest first: `{wishes: [wish]}`. A wish: `{id, gap_id, name, look_for, note, price_min, price_max, price_currency, found_at, prices_checked_at, bought_at, created_at, updated_at}`; `gap_id` and `look_for` (as in a gap, kept as it was when wished) are null for a wish added by hand. Bought wishes are not listed. |
| `POST /api/wishlist` | Adds a wish: `{gap_id}` for a gap of the current analysis (its name and `look_for` are copied; a hidden gap is brought back), or `{name, note?}` for one added by hand. 201 with the wish; 200 with the existing one when the gap is already on the list. 404 for an unknown gap; 422 for both, neither, or a name over 120 or note over 1000 characters. |
| `PATCH /api/wishlist/{id}` | Changes `name`, `note` and/or the price range `price_min`, `price_max` (numbers from 0 to 1,000,000; null clears one) and `price_currency` (three letters, `USD` by default). Only the fields sent are changed; clearing both prices clears the currency too. Answer: the wish. 404 when it is not on the list; 422 for a price out of range, a lowest price above the highest, or a currency that is not three letters. |

### Life-aware gaps

`GET /api/gaps` additionally returns `context`:

```
{
  life: null | {situations, work_dress, vacation_climate, vacation_weeks, style_words},
  prompt_dismissed: boolean,
  demo: boolean,
  climate: {used, place, shares, years, old, message},
  taste: {used: boolean, summary: string | null},
  suppressed: [{gap_id, name, situations: [situation_id], needs_confirmation: boolean}]
}
```

`climate.place` is a display name or null; `shares` is null, or an object with
`cold`, `cool`, `mild`, `hot`, each `{share, wet_share}`. Both are fractions:
`share` is the part of all observed days in that band, `wet_share` the part of
that band's days with at least 1 mm precipitation. `years` lists the four full
years observed (empty for the fixed demo). An unavailable lookup is still 200,
with `used:false` and an actionable `message`; kept older data has `old:true`.
No network call is made for an unanswered life questionnaire or the demo.

Each gap adds `situations: [{id, label, days_per_week, share, days_per_year}]`.
`share` is that situation's frequency / 7 times the weather shares of the
distinct days the gap serves, **not** a percentage of the gap's score.
Situations may overlap, so their shares need not total 1.
Vacation frequency is additionally scaled by weeks away / (365.25 / 7);
`days_per_week` still shows the answer for a week away.
Evidence days add `situation` and `share` when personalized.
`look_for` can additionally contain `fit`, `avoid_fits[]`, `avoid_patterns[]`.
Before answers, gap order, IDs, scores and existing fields are unchanged and
`situations` is empty. Home/exercise-only purchases get new `lounge`/`active`
kinds (including `light_active`, `warm_active`, `rain_active`, `rainwarm_active`
where exercise needs those properties); existing purchase IDs retain the
original construction.

The cache now also depends on answers, place/climate context and creation
dates used for long-owned items. Updating answers or place discards the main
cache; changed climate shares invalidate it too. Decisions are applied after
the cached analysis: confirmed `never_wear` holds back the same category and
dress/kind in the agreed situations, leaving outerwear, unrelated situations
and wishes alone. Held-back suggestions remain in `gaps` with
`state:"held_back"` and `held_back_by:[{gap_id,name,situations}]`; partially
affected open suggestions also have `held_back_by`. They do not consume the
open-suggestion limit when fully held back.
Old hides without consent remain direct hides only. Repeating
`POST /api/gaps/{id}/hide` with `reason:"never_wear"` confirms the displayed
situations, even if the original hidden suggestion is no longer missing.
Consent is kept separately for each closet in settings, matched to the hide's
timestamp, and removed on Undo. It is not in closet backups.
`context.suppressed` keeps those decisions visible even if the original gap
is gone; `DELETE /api/gaps/{gap_id}/hide` undoes one without re-analysing.

### Would this work?

| Route | What it does |
|---|---|
| `POST /api/would-this-work` | Starts a check of a piece the owner might buy against the open closet (`backend/closet/wouldjobs.py`, the check itself is `wouldwork.py`). By hand: JSON `{piece: {category, color, formality?, season?, pattern?, weight_class?, rain_proof?, name?, material?, silhouette?}}` (the item vocabulary; `category` and `color` are needed, `category` cannot be `other`; `weight_class` is `lightweight`, `midweight`, `heavyweight` or `super_heavy`). From a photo: multipart with `photo` (as for `POST /api/items`). 202 with the check (below), usually still `checking` or `describing`. 422 with a sentence for a wrong description; 400 for a file that is not a photo; 409 at once, with a sentence ending "Describe it by hand instead.", for a photo in the demo closet (never sent to Claude) or when no route to Claude can be used; 409 "Closet is already checking 5 pieces…" while 5 checks are still running. 400 for a photo over the upload limit. |
| `GET /api/would-this-work/{id}` | The check: `{id, state, way, piece, piece_words, answer, message, by_hand, started_at, finished_at}`. `state` is `describing` (Claude is looking at the photo, up to a minute), `checking`, `ready` or `failed`; `way` is `by_hand` or `photo`; `piece` is the description as checked (filled in: formality, season, pattern) and `piece_words` the same in one line ("Tan coat, smart casual, all year, midweight, keeps the rain off"). When `failed`, `message` says why and `by_hand` is true when describing it by hand gets round it (no route to Claude, the monthly limit reached, Claude could not tell what the piece is). 404 "This check is not known…" for an unknown id. |

The answer (`answer`, when `ready`): `{enough, message, verdict, verdict_words, reasons[], piece, fills: [{gap_id, name, score_before, score_after, gone, filled, days: [day], of_days, found_by[]}], goes_with: {days, suits, of, items[], examples: [{day, pieces, score, reasons[]}], text}, repeats: {items: [{id, worn, hardly_worn}], text, disliked[], disliked_text}, holds_back[], checked: {items, wears, days}}`. `verdict` is `fills_gap`, `adds`, `have_it`, `hard_to_wear`, or `too_small` (fewer than 8 pieces of clothing: `enough` is false and `message` says so); `verdict_words` is the same in plain words and `reasons` one or two sentences. `fills` are the gaps of `GET /api/gaps` that go away (`gone`) or get smaller with the piece, judged by the kinds of day they fail on with and without it, not by the score; `filled` is true when the gap counts as filled (it goes, or the piece frees at least half of its `of_days` failing kinds of day; see DECISIONS), `days` the kinds of day (as in a gap's evidence) it makes a good outfit on that nothing covers now. `goes_with.days` is how many of the `of` (40) kinds of day it makes a good outfit on, of the `suits` that suit the piece itself; `items` are item ids it pairs with most; `examples` are up to three outfits as `POST /api/outfits/today` gives them, the piece itself having the id `~candidate`. `repeats.items` are the owner's pieces that do the same job, most worn first, with their wears in the log, not counting pieces rated dislike; `disliked` are the ids of those, and `disliked_text` a sentence about them (or null). `holds_back` are sentences. Nothing is stored: checks are kept in memory, at most 5 (a new one drops the oldest finished one; one still running is never dropped), and are gone when Closet stops. A photo is never written to disk: it is held in memory only until its check is answered or fails, is never added to the closet, logged or backed up, and a description from a photo is recorded in the spending record with the purpose `would_this_work`.

## Trips

All behind the login, kept per closet (demo and real closet apart).

- `POST /api/trips/plan` — body `{place, first_day, last_day, occasion?, day_occasions?, can_wash?, leave_out?, pin?, weather?}`; works out the weather and packing plan, saves nothing. A trip is at most 30 days and starts today or later. Optional `weather` supplies every trip day as `[{date, low_c, high_c, rain}]`; it is intended for deterministic tests and browser checks, and those days return with `source: "given"`.
- `POST /api/trips` — same body; plans and saves. 201 with the trip.
- `GET /api/trips` — `{trips: [...]}`, upcoming first, then past; each summary's `uncovered` counts only days with no outfit, and `warnings` counts days with an outfit that has a warning.
- `GET /api/trips/{id}` — the trip: choices, `weather` (each day with `source`: `forecast`, `usual`, `given` or `unknown`), `plan` (`packed`, `days`, `basics`, `uncovered`, `warnings`, `notes`), `lines` and `packed` (ticked lines). `uncovered` lists only dates with no outfit; `warnings` lists dates that have an outfit with a warning. A day's `problem` explains why there is no outfit; `warning` explains what to watch out for when there is one.
- `GET /api/trips/{id}/weather` — looks the weather up again; `{checked, changed, days, message}`; changes nothing.
- `PATCH /api/trips/{id}` — `{ticks?: {line: bool}, occasion?, day_occasions?, can_wash?, leave_out?, pin?, replan?}`.
- `DELETE /api/trips/{id}` — 204.

Wrong input answers 422 with a sentence for the owner; an unknown trip 404.

### Life settings

`GET /api/settings` also includes `life` (null until answered) and
`life_prompt_dismissed` (false initially).
`PUT /api/settings` accepts either or both. A non-null `life` is a complete
questionnaire:

```
{
  "situations": {
    "work": 4, "everyday": 4, "going_out": 1,
    "lounging": 4, "exercise": 1, "vacation": 4
  },
  "work_dress": "smart_casual",
  "vacation_climate": "warm",
  "vacation_weeks": 2,
  "style_words": ""
}
```

Frequency values are finite numbers from 0 to 7, in days/week. The screen's
choices are 0 (never), 0.25 (now and then), 1 (about weekly), 4 (most days).
`work_dress`: `casual | smart_casual | business | formal`;
`vacation_climate`: `warm | cold | both`; `vacation_weeks`: 0–52, fractions
allowed; `style_words`: one line, at most 200 characters, trimmed but never
interpreted. Unknown/missing questionnaire fields and invalid values return
422 with a plain sentence. `life:null` restores the original analysis.
The demo reads fixed example answers and refuses edits to either life setting
(422); it never changes the owner's answers. All routes require the normal
login. No migration, new endpoint, key or external service other than
Open-Meteo's archive is involved.
