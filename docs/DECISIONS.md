# Decisions

What was decided and why, newest phase last. A fresh conversation should be
able to resume from this file, `BACKLOG.md` and the README.

## How the work is organised

The brief asked for eight phases with a stop after each. That was changed with
the owner once it was clear the recognition work does not depend on the app.

| Decision | Why |
|---|---|
| Two tracks: recognition and drawing, and the app | What the tagger reports and what the drawing shows is judged from render sheets and tagging reports, not from the installed program, and it will keep growing with the taxonomy. Gating the app on it stalled the app. |
| Track 1 (recognition and drawing) is reviewed continuously, with two checkpoints and no stops | The checkpoints are coverage of the taxonomy's visible values and accuracy on the owner's own photos. It needs no packaged build. Original phase 0 and the drawing half of phase 2 live here. |
| Track 2 (the app) has four main stops, then smaller ones | A stop is worth it only where something can only be checked on the owner's machine, where direction could change, or where money is spent. A: the program on the PC and iPhone (phase 1). B: the real wardrobe in (phase 2 and single-photo import, review queue and cost cap from phase 3). C: today's outfit (phase 4 with ratings from phase 6). D: gaps and shopping (phase 5). |
| Multi-item photos and video sweeps move behind the outfit builder | They are capture conveniences; the outfit builder and shopping are the two features the owner said matter most. Open for the owner to reverse. |
| The app stores the tagger's full answer, its schema version and the cutout for every item | This is what keeps the tracks independent: better drawings need no data change, and a taxonomy edit only means re-tagging, which is free on the Claude plan. |
| Template anchor points are fixed; category, formality, season and weight class are settled before stop C | The mannequin view relies on the anchors, and outfit and gap logic read those four vocabularies. Finer details can keep growing after stop C. |
| The repository is public | The owner made it public so that Actions minutes are free and unlimited for tests, builds and agent sessions. Commit metadata and tracked files were checked for personal details first. Going public cannot be recalled once copies exist, so the rule that photos and keys never get committed now protects against something irreversible. |
| App work can be done by Copilot cloud agents, orchestrated from a Claude session | The owner has a large monthly allowance of Copilot AI credits and wants to spare the Claude plan's weekly budget. Agents work from issues, open pull requests against `main`, and `ci` is the gate. `AGENTS.md` holds their rules; `copilot-setup-steps.yml` prepares their environment. Taste-driven drawing work stays in the Claude session with the owner. |
| The orchestrating Claude session merges pull requests when `ci` is green and its own review is clean | The owner's choice, for speed with several agents. It still stops and asks before merging anything that changes a recorded decision, touches releases or the release request file, or looks risky. |
| The first agent task is a bake-off | The same well-specified stop B task goes to Opus 5.5, Gemini 4 Argon and GPT 6 Astra (the strong models the owner's Copilot offers). They are compared on tests passed, review findings and rework needed, and the result decides which model gets which kind of task. |
| Bake-off result: Opus 5.5 is the default model for agent tasks; GPT 6 Astra runs alongside it where a second attempt is worth comparing | All three passed every check. Opus 5.5's storage view needed no rework: the screen matched the rest of Settings, it reused the app's own folder helpers, changed nothing else and documented its choices; it was merged (#13). GPT 6 Astra wrote the most thorough tests (loading, error, retry and offline states) but the weakest screen, and hard-coded folder names. Gemini 4 Argon had the fewest tests, changed a shared formatter and an unrelated behaviour, and skipped the decisions log; it is not used for now. One task each, so this is a first reading. The owner's rule: Opus 5.5 for most things, and the same task also given to GPT 6 Astra as a separate run when it costs nothing extra. The cost that remains is review time in the orchestrating session, so double runs are for tasks where the result is judged by looking (a screen, a drawing) or where the approach is open; both are compared on tests and screenshots, and only the better one gets a full review. |
| `main` is protected: changes arrive by pull request with `Lint and tests (Linux)` passing | The repo is public and agents open pull requests against it. Tests do not start by themselves on a Copilot pull request, and a run started by hand does not satisfy the rule; merging `main` into the pull request's branch from the orchestrating session starts a run that does, and also tests the result against the latest `main`. |
| The orchestrating session only orchestrates | The owner's instruction once the garment drawings were good enough for now: it writes the issues, starts the agents, reviews their pull requests and merges; it writes no feature code. Features are built by Copilot agents in waves of tasks that do not depend on each other, each issue naming its migration number so two agents cannot pick the same one. The numbers must follow the order in which the pull requests merge, because a migration only runs when its number is higher than the closet's current one: when a pull request with a migration is ready, its number is checked against `main` and changed if another has landed first (an agent caught this when `0003` was about to merge after `0004`). There is no `0002` and there must never be one. Agents do not edit `docs/BACKLOG.md`; the orchestrating session keeps it. Drawing work is parked in the backlog until the owner asks for it. |
| Finished agent work is reviewed before it is combined: changes that guard money or secrets by the orchestrating session itself, larger features also by a separate reviewer that has not seen the task being built; faults go back to the agent as a numbered list, each to be shown by a failing test first | The first two features reviewed this way (Insights, outfit ratings) passed all their own tests and still said untrue things to the owner or lost track of an outfit when an item was deleted. A reader who did not write the code, and was not told what to expect, found them. |
| What's missing is to be weighed by the owner's life, not a fixed grid | The owner, on seeing the screen: it "should have the ability to be informed by my style and context clues (ie. weather), as well as persona/situations (vacation, work, lounge, exercise)". Tasks #88 and #89: situations with how often they happen, the climate of the saved place, and taste from what he wears and rates. Until he answers the questions the analysis stays as it was. |
| Garment shapes are reviewed in a standing gallery, not ad-hoc sheets | The owner expects many rounds of review. `tools/make_review_gallery.py` builds one page with every garment, every taxonomy value, the weight ladder, trousers and shoes; it is published as a private Claude artifact where the owner marks each drawing "looks right" or "needs work" with a note. Marks are stored per drawing with the round they were made on, so a mark on an older drawing is flagged for another look after a rework. |
| The app's interface gets a design pass later | The owner wants the interface-design review run on the app, after more features exist; the current UI is known to need a lot of work. |
| Agents are started through the `start agent` workflow so the model can be chosen | Assigning an issue with the tools the orchestrating session has cannot name a model, and GitHub then picks one itself; the first agent run landed on a model the owner does not want and was cancelled. The workflow makes the same assignment through the REST API with a `model` field. It needs a fine-grained personal access token of the owner, kept as `COPILOT_AGENT_TOKEN` in an `agents` environment limited to `main`, because the built-in token may not assign Copilot. |
| Model ids for agents are GitHub's own, with dots: `claude-opus-5.5`, not the vendor's `claude-opus-5-5` | Found by trying: GitHub accepted the assignment with the vendor's id and then refused to start ("The selected model isn't available"); the dotted id started the agent. GitHub does not fall back silently when a model id is wrong. The ids for the other vendors' models are still to be found the same way. |
| CI runs on every pull request and push to `main` | It was manual-only while minutes cost money. |
| "Phase" in older entries below means the original numbering | Phase 1 is stop A, phases 2 and 3 are mostly stop B, phase 4 is stop C, phase 5 is stop D. |

## Phase 1

| Decision | Why |
|---|---|
| Phase 1 started before phase 0 was fully closed, at the owner's request | The paid API key is deliberately the last step. Phase 1 makes no Claude calls, so it needs no key. |
| SQLite through Python's built-in driver, with numbered `.sql` migrations and `PRAGMA user_version` | No ORM or migration library to package. A copy is taken before any migration; a database from a newer program is refused; a failed migration rolls back. |
| Program-wide settings live in `settings.json`, not the database | Passphrase hash, sessions, backup folder and model address are not part of a closet, so a restored or demo closet does not change who can log in. |
| The demo closet is a second closet under `demo/`, switched from Settings | Trying things never touches real data, the owner does not need command-line flags, and backups ignore it. Seven demo items are real open-licence photos with pre-made cutouts; the rest are drawn from templates. |
| Passphrase stored as a scrypt hash; session cookie is HttpOnly and SameSite=Strict; five wrong guesses lock login for five minutes | Standard library only. The server listens on 127.0.0.1; Tailscale serve is the only way in from outside. |
| Uploads carry a client-made key | A retry after a dropped connection returns the first item instead of creating a duplicate. |
| The cutout queue is rows in the database, processed by one worker thread | Nothing is lost on quit; interrupted jobs resume; jobs wait while the model is missing instead of failing; three attempts before an item is marked failed. |
| The uploaded full-size file is never written to disk | Only the 1600px photo, its cutout and thumbnails are stored, all WebP. |
| Backups are dated database snapshots plus an add-only copy of the images, 14 snapshots kept | Snapshots use SQLite's own backup so they are consistent while the app runs. Restore moves the current closet aside instead of deleting it. |
| ffmpeg is left out of the phase 1 program | Video arrives in phase 3. The spike proved it can be bundled, but it adds about 105 MB to a file that unpacks on every start; phase 3 will decide between bundling and download-on-first-use like the model. |
| CI and release workflows are manual-only for now | The owner has not yet approved spending Actions minutes. Files travel between release jobs through a draft release, because artifact storage is exhausted. |
| Outbound HTTPS uses the computer's own trusted certificates (`truststore`), with a bundled certificate file as fallback | The first Mac build could not download its model. The likely cause, not yet confirmed on the owner's Mac: a packaged Python has no certificate store on macOS, so the HTTPS connection fails and was reported as no connection. The system store also works on a work computer whose network adds its own certificate. The release build now checks an HTTPS connection from the packaged program, and a certificate failure has its own message. |
| A release is started with the `release` workflow's Run button (or the same call from the orchestrating session) | For one day, before the workflows were on `main`, a release was started by editing a request file; that trigger is removed now that the normal route works. Windows and macOS can be built separately. |
| A newer program that finds an older copy running asks whether to close it and use the new one, instead of only opening the old one | Before, a downloaded update looked like it had not installed, because double-clicking it opened the copy still running. The question is a plain window (a message box on Windows, a dialog on the Mac); a copy started at login (no tray icon) is never held up by a question, and the same version, a newer one or a copy run from source is still simply opened. The lock file holds a random token, and a copy quits when `POST /api/instance/quit` sends it: only something that can read the closet's own folder can do that, so this adds no way in from the browser (a page cannot set the header without the server allowing it, and it does not). Copies from 0.2.0 and before have no token, so they are stopped by their process id: on the Mac that is the same as Quit; on Windows the process is ended, which SQLite survives, and it is a one-off for those versions. After replacing, start at login is pointed at the new program, and the new copy waits for the old one's port so phone access keeps working. Checking whether a port is free now uses the same socket option the server uses, so a port whose last connections are still closing is not skipped. |
| Closet updates itself from the latest published GitHub release, checking once a day and on demand | The owner asked for it. Only `releases/latest` of this public repository is asked, without a token and with a plain `Closet-updater` User-Agent, so nothing about the owner is sent; drafts (a release still being built) and pre-releases never count. No new dependency: `urllib` and `hashlib`. Offline and GitHub's rate limit are noted quietly and tried again an hour later. |
| A download is checked against the SHA-256 `digest` GitHub's releases API gives for each asset, not a separate checksum file | GitHub works the digest out itself when the file is uploaded, so it needs no change to the release workflow (which agents may not edit) and cannot drift from the file. It comes over the same HTTPS connection as the release, so it guards against a broken or swapped download rather than against GitHub itself, which a checksum file in the same release would not do any better. A release without a digest is not installed. |
| "Ask me first" is the default; "Install updates by themselves" and "Never check" are the other choices | An update restarts the program, which closes the page for a moment and could interrupt the owner in the middle of adding clothes; they should see it first. Ask-me-first still downloads and checks the new version ahead, so Install is quick. "Never check" still allows Check now. |
| Every closet is backed up before an update, and the update stops if that fails | A local snapshot of the real and demo closets goes into `backups` (`pre-update-…`, the last three kept), plus the usual backup into the owner's folder when one is chosen. The database is the one thing an update could damage. |
| The program is swapped by renaming, and the old program watches the new one start, putting itself back if needed | Windows lets a running exe be renamed, not overwritten: it becomes `Closet.old.exe`. On macOS the downloaded zip is unpacked with `ditto` beside `Closet.app`, checked with `codesign --verify --deep --strict` and swapped in (old kept as `Closet.old.app`); the quarantine flag is removed only from that bundle. A copy of the old program started with a hidden `update-watch` command starts the new one with `--replace` on the same port, so the existing "newer copy replaces older" hand-over keeps the address and login; if the new one has not written its lock file and answered within 60 seconds, it is stopped, the old program is put back and started (with the copy of a closet from just before the update, if the new program had already upgraded it beyond what the old one can open; the upgraded copy is kept in `backups`), and the reason is written to a small file the program reads (the watcher never writes `settings.json`, to avoid two writers). The new program removes the old one once the watcher reports success. Programs started this way get `PYINSTALLER_RESET_ENVIRONMENT=1`, so the new one does not reuse the old one's unpacked files. |
| Saves are sent with `keepalive`, and waiting saves are sent on `pagehide` or when the page is hidden | A change made just before a reload or close used to be lost: the browser cancelled the save, and a text field only saved when it lost focus. Every save with a small body (an item edit, a wear, a rating, a trip tick, settings) is now a keep-alive request, which the browser finishes after the page is gone; it still carries the login cookie and goes to the same address. Photos are not (too large for it), nor questions the app can call off (Today's outfits, a trip plan, a figure). Browsers allow 64 KiB of such bodies on their way at once and refuse one that would go over, so the app counts its own and sends a save the usual way past 48 KiB. When the page is hidden or closed, an edit still being typed in an item's text fields is saved, and trip ticks waiting behind another are sent at once instead of one after the other. Saving on hide means switching to another app also saves what is typed, which is what the owner would expect. |
| Saves (`POST`, `PUT`, `PATCH`, `DELETE`) go straight to the network, past the service worker, where the browser supports it (static routing, `addRoutes` in `sw.js`) | A note typed just before a reload was still sometimes lost (#147; the browser test failed 10 times in 30): the save left the page, but with the service worker in its path the browser sometimes dropped it as the page went away; with the worker out of the way it always arrived. The worker never kept anything but `GET` answers, so nothing is lost by skipping it. Browsers without static routing (Safari, Firefox today) still pass saves through it as before. |

## Stop B

| Decision | Why |
|---|---|
| The storage view adds up known folders on every request, nothing is stored | Sizes are always current and there is nothing to keep in step. It reads only the closet's images, its database (with SQLite's `-wal` and `-shm` files), and the shared `models`, `logs` and local `backups` folders, without following links, so nothing outside the data folder is touched; a backup folder the owner chose elsewhere is not counted. The total is the sum of those parts (small files such as `settings.json` are left out). The item count includes archived items, since they take space too. Sizes are shown with 1 KB = 1000 bytes, as the model download already does and as macOS does; Windows Explorer counts 1024, so its numbers come out a few percent lower. |
| The tagger lives in the backend as `closet/tagger/` (schema, taxonomy, prompt and API route, plan route, route order, and `models.json`); the bench's modules of the same names are that code | The app needs it and there must be one copy, so a prompt or taxonomy change cannot reach the bench and miss the app. Each bench module replaces itself with the backend module (`sys.modules`), so `closet_bench.claude_cli` *is* `closet.tagger.claude_cli` and existing imports, tests and tools work unchanged, including tests that swap out a function. `closet_bench` puts `backend/` on the import path itself. The drawing code (templates, renderer, fills) stayed in the bench at first (it has since moved, see below); the list of shoe styles the drawing has a shape for moved into the tagger's taxonomy, because the schema reads it and the tagger must not need the drawing code. The bench's taxonomy test and the vocabulary test now import the tagger directly. |
| Whether the plan route can be used is checked with `claude auth status`; whether the API route can be used, by whether `ANTHROPIC_API_KEY` is set | `claude auth status` reads the local login, asks Claude nothing and exits 0 when signed in, so Settings can check it on every visit for free. It runs with the API key removed from its environment, as a real plan call does, gives up after 5 seconds, and its output (which names the account and the config folder) is never returned or logged. The keychain is meant to hold the key (see "Before phase 0"); since the API key box in Settings, a key saved there (service "Closet", account "anthropic-api-key") counts too, and wins over the environment. Only a key's presence is looked at. |
| The `anthropic` package is in the packaged program, pinned with what it needs (part 2) | Both routes need it: the API route to call, the plan route for the strict answer schema it passes to `claude -p`. The program's self-check imports it and builds that schema, so a build that left it out fails its smoke test. |
| The drawing code (templates, renderer, fills) lives in the backend as `closet/drawing/`; the bench's `templates`, `illustrate` and `fills` are that code | The app has to draw an item from its tags, and there must be one copy, so a template change cannot reach the review gallery and miss the app. Done the same way as the tagger: each bench module replaces itself with the backend module, so existing imports, tests and tools work unchanged. Nothing about the drawings changed: the review gallery was regenerated before and after and is byte-for-byte the same, the 36 drawing fingerprints in the bench's tests pass untouched, and regenerating the demo closet changes no file. |
| The app's program does not include OpenCV; the drawing code imports it only inside the functions that read a photo | Only the bench's "traced" style and the fills measured from a cutout (dominant colour, swatch, stripes, print) use it, and the app draws from tags. Moving those functions elsewhere would have split the module the bench imports; a delayed import keeps one module and costs nothing. `numpy` and Pillow, which the drawing code imports at load, are already in the program. The packaging spec excludes `cv2` so a build machine that happens to have it cannot bundle it. The moved code keeps its own style; the backend's linter skips four of its rules for those three files rather than have them rewritten. |
| The app draws an item through `closet.drawing.item`: from its stored tagger answer, or from the coarse fields alone; it never raises | The item screen must always open. A value the tagger's vocabulary does not know (or a field an older answer lacks) is dropped and the rest is kept; if drawing still fails, the plainest drawing of the category is returned. A bag, belt, hat, scarf, "other" or unknown category gives no drawing, as there is no shape for it; the app shows the photo. Drawn in style B on a solid fill of the item's colour (its own hex if it is a valid one, else its colour word): a pattern needs the photo, so it is not drawn here yet. The packaged program's self-check draws a shirt this way, so the smoke test proves the package was bundled. |
| "The same photo" means the same file as the owner chose it, compared by its SHA-256; the browser sends that hash with the upload | The page shrinks and re-encodes every photo before sending it, so the bytes the server receives can differ between browsers and between the phone and the computer; the chosen file's bytes do not. The server cannot check a hash of a file it never sees, which is acceptable for a single-user app behind its login. Without a hash (another client, a browser without the crypto API) the server hashes what it received. Stored in `photos.source_sha256` (migration `0005`); photos added before it get their received-bytes hash, the best that is known. Archived items count; a deleted item's photos are gone, so its photo can be added again. A photo of the same garment taken twice is a different file and is added; telling those apart is left to the review queue. A duplicate answers 200 with the existing item and `duplicate: true` rather than an error, so an import just moves on. |
| Bulk import uploads two photos at a time and keeps its list in the browser (`localStorage`), not the files | Two lets one photo upload while the next is being shrunk, without crowding the computer that also removes backgrounds. A browser cannot reopen files the owner picked or dropped after the tab closes (not on the iPhone, and not for dropped files anywhere), and copying every photo into browser storage would double the space a large import takes. So after a closed tab or a restart the list of names and upload keys survives, and the owner chooses the same photos or folder again. Each file is matched to its row by name, size and date and sent with that row's first key, so the server recognises the ones that went in without processing them again, and its duplicate check catches anything else. Files that went in are not skipped by the page itself: the server is the one that knows whether that item has been deleted since. |
| While Closet cannot be reached, imports wait instead of failing | An upload cut off by a lost connection goes back to waiting and the queue carries on when the page sees Closet again, so a restart in the middle does not leave a list of failures. |
| The packaged program is built and smoke-tested on Linux by the `package-check` workflow on every push to `main`, on pull requests that touch packaging or what the spec bundles, and by hand | Changes such as the tagger, the drawing code and the `anthropic` package each changed what the program must include, and a broken build was only found when a release was asked for. Linux is the cheapest runner and shares the spec, the pinned requirements and the smoke test with the release, so a missing module, data file or migration shows up there; Windows and macOS are still only built by the release, and the background-removal check (which downloads the model) stays there too. This narrows "packaged build runs on demand" (see "Before phase 0") for Linux only. No cache and no uploaded build: storage is still exhausted, and a run takes about 4 minutes without them. The smoke test now also checks the page's scripts are served with the right type, a demo drawing is served, every migration is bundled and both closets reach the latest. |

## Tagging each item (part 2)

| Decision | Why |
|---|---|
| The API route is only used when the owner turns on "Allow the API key" in Settings, and only with a monthly limit; it is off by default, for the plan route nothing is needed | The API key is billed per photo. A key that is set but not allowed counts as no route: items wait. The switch and the limit are kept in `settings.json` with the other program settings, not per closet. A switch turned on before limits existed counts as off until a limit is set. |
| Tagging jobs are rows in the same `jobs` table as cutouts (`kind = 'tag'`), worked by a second thread with the same rules | Nothing is lost on quit, an interrupted job resumes, three attempts and then failed, as for cutouts. A separate thread keeps a slow Claude call (up to minutes on the plan) from holding up cutouts. A job is queued when the cutout is ready, in the same transaction. |
| While no route to Claude can be used the job waits and does not use up an attempt; the worker looks again every minute, when a cutout finishes, when the settings change and when Settings checks the routes | "Not signed in" or "out of credit" is not the item's fault. A route that looked usable but turns out not to be (the plan's limit was reached mid-call) puts the job back the same way. The routes are worked out again before each item, so turning the API key off stops it at once, not after the queue. A job left half-done (a quit, a crash) is put back at the start of the next round, and failed once it has used its three attempts. |
| The tagger's whole answer is stored with the item (`tag_answer`, JSON), with the schema version, route, model and time | Better drawings later read the details from it without asking Claude again, and a taxonomy change only means tagging again. `SCHEMA_VERSION` in `closet/tagger/schema.py` says which shape an answer has; a test holds a fingerprint of the schema and fails until the version is raised. |
| The answer fills `name` (only when there is none), `category, color, color_hex, pattern, formality, season, silhouette, material`; a field the owner has set is never changed | `source` records who set each field: the owner's changes are `user`, the answer's are `ai`. A field is filled when it is empty or was filled by an earlier answer, so describing again updates suggestions and leaves the owner's own words alone; a name typed at upload counts as the owner's. `color_hex` comes from the colour's name. |
| Items added before this version are not queued by the migration; the owner can use "Describe it again" on any of them | Queuing a whole closet at once on first start would surprise the owner (and, with the API switched on, spend money). |
| The demo closet is never sent to Claude; its 30 items carry an answer made in advance by `tools/make_demo.py` from what it already knows about each one (route `demo`) | The demo shows the same screens as a real closet with no account and no cost. A photo added to the demo closet gets its cutout but is not described, and "Describe it again" is refused there. An older demo closet gets the answers the next time it is opened. |
| Only the kind of a tagging failure is logged, never Claude's reply, a photo, a key or a folder; the owner sees a plain sentence | Claude's reply can quote what it saw; the reason shown says what to do next. |
| A cutout or description that fails for good shows the reason its job recorded under "Details" on the item, and writes it once to the log at WARNING with the item's id, after keys, tokens, e-mail addresses and paths outside Closet's folder are taken out (`closet/failures.py`); each attempt still logs only the kind of failure | Asked for in issue #103: an unknown failure could only be read from the `jobs` table with a terminal. This narrows the row above: the recorded reason can quote up to 200 characters of what Claude Code printed, and it now reaches the page and the log once. ### Review queue

| Decision | Why |
|---|---|
| A field is doubtful when the tagger filled it and its confidence is below one threshold per kind of field: category 0.70, colour 0.85, pattern 0.70, formality 0.80, season 0.80, silhouette 0.70 (`UNSURE_BELOW` in `closet/review.py`, the one place they are written) | Starting values, to be tuned once the owner's own photos have been through the bench. In phase 0 every wrong answer came with a confidence of 0.8 or less, and one wrong colour came at exactly 0.8, so colour is asked about below 0.85; formality and season are judgement calls, and the tagger got formality wrong at 0.7, so 0.8; category, pattern and silhouette were always right in those runs, so they are only asked about when the tagger itself says it is guessing (below 0.7). Higher thresholds ask about more; the aim is a queue short enough to clear after an import. Material, the name and the details carry no confidence (or are not fields the owner sets) and are not reviewed. |
| Confirming marks the field as the owner's (`source` `user`) and sets its confidence to 1; a new endpoint does it, changing a value uses the existing `PATCH` | The tagger never overwrites a field the owner set, so a confirmed or changed field stays out of the queue after "Describe it again" with nothing new stored; no migration was needed. Confidence 1 matches what a `PATCH` already stores. |
| The silhouette is one field in the queue | The tagger gives one confidence for the whole silhouette, and the item stores one source for it, so confirming or changing any part of it makes the whole silhouette the owner's. |
| "Skip for now" changes nothing; skipped items are shown again the next time the screen opens | Skipping is "not now", not "this is right". Within one visit the screen moves on and offers to go round again. |
| Waiting and failed items are counted beside the queue, not in it; in the main closet an item whose cutout is still being made counts as waiting, since describing follows it; archived items are left out | A field Claude has not answered yet has nothing to confirm; the screen says how many are still waiting or failed and links to them, so an empty queue is not mistaken for "all done". |
| In the demo closet the answers made in advance carry their confidences; five items have doubtful fields: Madras plaid shirt (colour 0.5, season 0.65), marl turtleneck (colour 0.55, silhouette 0.6), white leather sneakers (category 0.6, formality 0.6), tan chore jacket (category 0.65), grey wool trousers (formality 0.75) | So the Review screen can be tried without a Claude account. The values are in `UNSURE` in `tools/make_demo.py`; an older demo closet picks them up the next time it is opened, for fields still marked as the demo's. |
| The badge's count is asked for again when the screen changes, the closet changes or the connection comes back; offline the screen says reviewing is unavailable | One small request; the service worker does not keep the queue, as an old queue could offer to confirm fields already changed elsewhere. |

### Correcting an item, and its history

| Decision | Why |

A feature (V insert, toe cap ...) is kept as `"yes"` or `"no"`, so the owner can both add one Claude missed and remove one it imagined. When only the limit stands in the way the answer says so and offers the picker | A typed correction can make up to four billed requests; it must not go around the limit the owner set, or be missing from the record. |
| In the demo closet picking and the history work fully; a sentence is answered with a sentence that the demo closet is never sent to Claude | As for "Describe it again" there. Each history entry keeps the drawing from before it with a fingerprint of everything the drawing is made from, so whenever an undo brings the item back to a state it had, in any order of undoing, that state's drawing comes back: the hand-made one once the item is as it was. |
| Every change to the description is kept in a `changes` table with its parts before and after, when, and who (`owner` or `claude`): Claude's answer arriving (also when it says the same again), a field changed, details picked, a correction by sentence, an undo. Parts are found by comparing the item before and after, so any route of change records what really moved | The owner can see why the drawing is as it is, and can go back. Notes, wears and the laundry are not part of the description and are not kept here; the name and material are, because Claude's answer fills them. |
| Who set a field is part of what is recorded: confirming fields in the review queue, or a `PATCH` giving the same value, makes the field the owner's and is an entry ("You confirmed the colour as navy"); Claude only growing more or less sure of a value is kept in its entry but not said | Otherwise undoing an earlier change could not put back who set the field, and the history would not explain why "Describe it again" leaves a field alone. |
| Undoing a change gives a field back to the tagger with the value Claude's current answer gives it (the rule an arriving answer follows, `tagjobs.fill`), not the value stored before the change, when an answer has come since | Example: the owner sets the colour to green; Claude describes it again as cream (green stays); undoing the owner's change gives cream, marked as the tagger's with its confidence, matching the drawing. ### The outfit engine

The rules live in `backend/closet/outfits.py`; every number is a named constant at its top. These are the choices someone could have made differently.

| Decision | Why |
|---|---|
| Two passes: strict rules first, then the same rules as penalties with a warning each | A big closet should never be offered a hoodie on a business day, but a small one should still get an answer ("the sneakers are more casual than a business day calls for; nothing better is clean") instead of nothing. The relaxed pass runs only when the strict one finds no outfit at all. Dislike, archived, laundry and the layering order are never relaxed. |
| The day is dressed for at the low plus 30% of the way to the high | A layer is easier to take off than to find. Warmth is counted in points per piece (by place and weight class) against a target that falls about one point per 2°C; being too cold costs more than being too warm, except at 24°C and above where nothing can come off. |
| Bands: no mid or outer layer, no cool-season pieces and no heavy base tops at 24°C and above; an outer layer whenever the closet has one at 8°C and below; no shorts below 18°C; no sandals below 20°C or in rain | Round numbers for New York that the owner can change in one place. Between the bands the warmth points decide. |
| Weight class comes from the item's own weight class when it has one, then words in its material, then words in its name, then its category (a warm-season item one class lighter) | The item's own weight class is taken from the tagger's stored answer (see "What the engine knows about the cloth" below). "Plaid flannel shirt" and "Burgundy cable sweater" say how heavy they are in the name; the category alone would make every shirt midweight. Specific words win over generic fibres ("merino wool" is midweight). |
| Layering: each layer is at least as heavy and as bulky (oversized counts one class bulkier) as the one under it; a base top that is midweight or lighter and not oversized goes under anything | This is the owner's rule (no heavy overshirt under a thin bomber). Without the exception a standard tee could not go under a light windbreaker. |
| Places: base is a tee, shirt or polo; mid is a sweater, a hoodie, a shirt (only over a tee) or a jacket (only under a coat); outer is a jacket or coat | An open shirt over a tee and a blazer under an overcoat are both normal; a shirt over a shirt is not. Sweaters and hoodies are never the only top, which leaves out a turtleneck worn alone. |
| Formality: every piece within one step of the occasion and of each other; the outer layer may be two steps away; business never gets hoodies, sneakers, sandals or shorts, and formal also no tees, polos or jeans | A good overcoat goes over jeans and a chore coat over a suit on the way to work; the rest of the outfit has to agree. The category bans catch items tagged too generously (leather sneakers tagged smart casual). The mood moves the formality aimed for by half a step in the score, not the hard limits. |
| Colour: neutrals are black, white, grey, navy, tan, brown, cream, olive and light blue, and blue jeans; at most one other colour unless the colours are tonal (same family, or stored hues within 25°) | Light blue shirts and olive trousers behave as neutrals in menswear. "multi" counts as a colour that is never tonal with another. |
| Pattern: plaid, floral, camo, graphic and "other" are loud, stripes are quiet; at most one loud pattern and at most two patterned pieces | A Breton stripe under a plaid overshirt is a classic mix; two plaids are not. |
| Rain: sandals never; suede, canvas, linen and silk shoes and outer layers cost points; boots and an outer layer whose name or material says it sheds water score higher; otherwise the owner is told to take an umbrella | The stored fields say no more than that about rain. |
| Items in storage are used, with a small cost and a note to get them out | The demo's only overcoat is in storage; leaving it out would leave a cold day without a coat. Items in the laundry are never used: the laundry state (`laundry` other than `clean`) or the location `laundry`. |
| Worn in the last 4 days costs points, most for today and less each day, half as much for bottoms, outer layers, shoes and accessories | Jeans, coats and shoes are worn again more often than tops. It is a preference, so an item worn yesterday is still chosen when there is nothing as good. |
| A build-around item may break the day's rules (shorts at 5°C, a disliked shirt) and the outfit says so | The owner asked for it. Archived and laundry items cannot be built around. |
| Outfits offered differ in at least two of base, mid, outer, bottom and shoes; if the closet cannot give enough, one | Accessories do not count. The next outfit is chosen by score less a small cost per piece shared with one already offered, so the list is not three versions of the same outfit. |
| Only the best six candidates for each place, plus the warmest and the lightest, are combined | Every combination of a few hundred items is millions; this takes well under a second and keeps a warm coat in reach on a cold day. |
| Accessories are added after the outfit is chosen: a scarf at 8°C and below, a hat at 4°C and below, a belt with trousers or jeans (preferring the shoes' colour); a bag only when built around | They do not change which outfit is best, and shoe-matching leather is the one rule worth applying. |
| Scores start at 80 for an outfit that breaks nothing; loved pieces, one accent colour and rain-ready pieces add, distance from the formality aimed for and warmth off target subtract | So that 100 is rare and a relaxed-pass outfit is visibly lower. |
| The API answers 422 for a build-around id not in the open closet; the engine on its own answers with a `missing` sentence | A wrong id from the screen is a bug to show; the engine itself never raises for a closet's contents. `suggest` takes `worn_days_ago` from the request; `today` fills it from the wear log. |

### Today's outfits by themselves

`POST /api/outfits/today` fills the day for the engine: the weather (`backend/closet/weather.py`), the wear log and the laundry (`backend/closet/today.py`). The engine itself is unchanged; it already read the laundry state as the wear log stores it (`clean` or `laundry`).

| Decision | Why |
|---|---|
| Where the owner is, is a place saved in the program's settings (`settings.json`), not in a closet. Until the owner chooses one it is **New York** (the owner's home), so Today has the real forecast from the first open; a place the owner chose always wins, and removing it goes back to New York. It is chosen by name, or with **Use my location**: only when the owner taps it, the browser is asked for its position, which is rounded to two decimals (about a kilometre) and named by OpenStreetMap's reverse geocoding (Nominatim; only those coordinates are sent), then saved like a chosen place. Where the browser refuses, or the page is not a secure context (the phone over plain http), the button says so in one sentence and the search stays. It is never guessed from the network address | Real weather with nothing to set up matters more than a blank form, and the owner lives in New York. A guess from the address is often a city away (or the internet provider's city), and the owner should know exactly what is used, so the browser's position is only ever asked on a tap and the saved name is shown. Open-Meteo has no reverse lookup; Nominatim needs no key and gets only the rounded coordinates. Its time zone is left to Open-Meteo (`auto`). Both closets share the place, so the demo closet works like the real one. No migration. |
| The weather comes from Open-Meteo (`api.open-meteo.com`, places from `geocoding-api.open-meteo.com`) | No key, no account, free for personal use, and a daily low, high, chance of rain and weather code is all the engine needs. |
| Privacy: the only things sent to Open-Meteo are the words typed into the place search and the saved place's latitude, longitude and time zone. Nothing about the closet is sent, and the place is not written to the logs | Settings says so in one sentence next to the search. |
| A forecast is kept for an hour (in `settings.json`) and reused; it is asked again sooner when the day has changed at the place | Today's forecast barely moves in an hour; this keeps the screen fast and the requests few. Keeping it in the settings file means it survives a restart. |
| When Open-Meteo cannot be reached, the last forecast for the same place is given back marked as old; with none, the answer says so in plain words (not an error page) | The closet still works without the internet. Changing the place forgets the forecast. Today's outfits use an old forecast only when it is for today. |
| With no forecast for today (offline, the service down) and no temperatures typed, Today dresses the owner for a mild, dry day (14–20 °C; `source: "mild"`) and says the weather could not be fetched, with **Try again** and **Type temperatures** | Today never shows no outfit just because the weather is missing; a mild day gives ordinary outfits, and the notice makes clear they were not chosen for the real weather. Typing temperatures is behind **Change**, no longer the first thing shown. |
| Tests never reach the weather or place-name services: a `conftest.py` fixture makes every backend test's lookup fail unless the test fakes it, and every browser-test backend runs through `tests/e2e_backend.py`, which does the same | A forgotten fake would otherwise call Open-Meteo (now that New York is the default, any Today call would) and make tests depend on the network. |
| A day is rainy when the highest chance of rain is 50% or more; when the forecast gives no chance, when its weather code is drizzle, rain, snow or storms | The engine's rain rules (no sandals, no suede, take an umbrella) are about wet ground and wet shoes, which snow shares. |
| Any of the low, high and rain given in the request wins over the forecast, field by field; with both temperatures and rain given the weather is not looked up | So the screen can let the owner correct a forecast ("it's warmer than that") without losing the rest. With temperatures given and no forecast, rain is taken as no. |
| Days since an item was last worn are counted from the computer's local date, the same date wears are recorded on | A forecast for a place in another time zone may be for a different calendar day; the wear log's own date keeps "worn yesterday" meaning yesterday. |

### What's missing (gaps by rule)

The rules live in `backend/closet/gaps.py`; every number is a named constant at its top. These are the choices someone could have made differently.

| Decision | Why |
|---|---|
| Gaps are found by running the outfit engine itself over 40 days: cold, cool, mild and hot (low/high 0/6, 8/14, 15/21, 25/31 °C), each dry and rainy, for each of the five occasions | The engine is what the owner sees every morning, so a day it cannot dress well is the gap that matters. The four bands land on either side of its own thresholds (coat at 8 °C and below, no layers at 24 °C and above). A real year of weather was not used: it would need a place and a clock. |
| A day fails when the engine returns nothing, has to use a piece that breaks a rule, puts together pieces that clash, is well short of warm or well too warm, says "take an umbrella" in every outfit it offers, puts suede or canvas shoes on a rainy day, or cannot make three outfits that differ | Each is turned into the one piece that would fix it (a coat on a cold day without one, a sweater when there is a coat, light trousers when only jeans suit a hot business day). Rain counts only when none of the three outfits keeps it off, since the owner can pick the second one. |
| Days count by occasion: casual and smart casual fully, business 0.7, sport and formal 0.3 | Sport and formal days are rare; a gap that only shows on them should not top the list. |
| A thin place is a place where every outfit offered for a day uses the same piece and nothing else suits; for a coat on a cold day, a lighter one does not count as a second | One pair of smart shoes or one coat is fine until it is at the cobbler's. |
| An orphan is an item in at most one of the grid's outfits whose partners of one kind (bottoms for a top, tops for a bottom, and so on) all clash with it; the gap is one plain, neutral piece of that kind | A loud shirt with no plain trousers is the example the owner gave; one purchase brings it into use. |
| From the wear log: an item worn at least 4 times and at least 3 times the average of the others of its category, in a log of at least 10 wears, asks for a second one like it, unless one is already owned | Fewer wears say nothing yet. Never-worn items are listed in a note, not as gaps: buying more does not help them. The log's period comes from its own dates, not the clock. |
| The basics are ten: a plain neutral tee, a white or light blue oxford, a plain neutral sweater, dark jeans, neutral chinos or trousers, a warm coat, a rain-proof outer layer, plain sneakers, smart leather shoes and a leather belt | Taken from the classics in `docs/menswear-reference.md` and kept short: each is something most outfits the engine makes need, or a day it cannot dress without. Suits, ties, polos and boots in particular were left out; a basic the owner owns but rated dislike is still missing. |
| Findings that the same purchase would meet are merged: same category and kind (warm, light, rain) and formalities within two steps; the merged score is the best finding plus a quarter of the others, up to 100 | One rain coat fixes every rainy day; listing it once per occasion would bury everything else. Two kinds of smart trousers far apart in formality stay separate. |
| The list is cut to 8, and a closet with fewer than 8 pieces of clothing gets a sentence instead | A list of everything is no help, and a three-item closet is missing nearly everything. |
| Items in the laundry count as owned; archived items do not; disliked items are owned but never used | A shirt in the wash is not missing. The engine already never picks a disliked item, so it is not something to build on. |
| The analysis reads the engine's own pieces, options and rules (functions in `outfits.py` whose names start with `_`) and does not change `outfits.py` | The two cannot disagree about what suits a day. If the engine changes, the gaps follow. |
| The API keeps the last answer per closet and reuses it until an item or a wear changes; a wash, a timestamp or a cutout does not count | The analysis takes about a second on the demo closet and about four on 300 items (40 runs of the engine, each bounded by its own six-candidates-per-place search, not by the size of the closet). |

### What's missing: how the owner lives

This extends the fixed grid above **only after answers**. Before answers the
old analysis is byte-for-byte unchanged (including scores and order); **Not
now** dismisses the invitation, not the ability to answer later. There is no
migration: `life`, `life_prompt_dismissed`, and `climate` live in `settings.json`.
No dependency or change to `outfits.py` is needed. `gaps._run_grid` accepts an
optional set of days/moods; its default is still the original grid.

`life.SITUATIONS` is the one mapping table, with a reason beside every row:

| Situation | Occasion / mood | Weather and pieces | Why |
|---|---|---|---|
| Work | The chosen casual, smart casual, business or formal / sharp | All home bands; all pieces the engine permits | The actual workplace, not an assumed office dress code. |
| Everyday | casual / usual | All home bands; ordinary engine pieces | Errands and seeing friends. |
| Going out | smart casual / sharp | All home bands; ordinary engine pieces | A step up for dinner, not an assumed black-tie calendar. |
| Lounging at home | casual / relaxed | Indoors at 18–22°C, no rain; tees, hoodies and soft relaxed trousers/shorts/knits, never outdoor coats or shoes | There is no loungewear category. Coverage asks for two suitable tops and bottoms, rather than asking the outdoor engine to insist on shoes. |
| Exercise | athletic / relaxed | Home bands; casual/athletic tees, hoodies, shorts, sneakers, jackets/coats, and athletic or soft trousers | Never call jeans or tailored trousers exercise clothes; keep warmth, lightweight and waterproof requirements in the suggested purchase. |
| Vacation | casual / relaxed | Warm = mild/hot; cold = cold/cool; both = all; wet/dry equally likely; ordinary engine pieces | Destination weather is not home weather. |

Frequencies: never = 0, now and then = 0.25, about weekly = 1, most days = 4
days/week. Situations can overlap; they are not forced to sum to seven.
Vacation means that frequency **during weeks away**, scaled by weeks/year
divided by 365.25/7. No weeks away means no vacation gaps.
The optional style line is at most 200 characters, shown verbatim and reserved
for future shop search; no model or keyword rule reads it.

Lounging's soft words (`SOFT_WORDS`) are jersey, fleece, sweat, jogger, knit
and stretch; fits, when known, must be regular, relaxed or oversized. Tees and
hoodies must be casual/athletic; soft bottoms must also be casual/athletic.
These are proxies, not knowledge of softness, pyjamas or the difference
between a going-out tee and a home tee. A hoodie can layer at home, but is not
counted as a base top. Exercise cannot distinguish running, gym work or other
sports, moisture-wicking fabric, support or protective equipment. The screen
must not promise that it can.

Since #111 an item can have a **kind** from the owner's taxonomy (`details.garment`:
the tagger's answer, or the owner's choice under Shape on the item page;
`today.cloth` passes it to the engine as `kind`). When the kind is known it
decides, and the soft words are not read:

| Decision | Why |
|---|---|
| Lounging takes the taxonomy's loungewear (`LOUNGE_KINDS`) and the soft everyday kinds `HOME_KINDS` (sweatpants, joggers, open-hem sweatpants, fleece pullover, sweatshirt, hoodie, shorts) whatever their formality; sportswear that is not one of those (tights, track trousers) only as a tee or hoodie; any other known kind of trousers, shorts or knit is not for home | A name like "Stretch chinos" no longer makes chinos loungewear, and a pair the owner calls lounge trousers counts even if it was tagged smart casual. |
| Exercise takes the taxonomy's activewear (`SPORT_KINDS`, which includes the fleece pullover the owner's file files there) and `EXERCISE_KINDS` (sweatpants, shorts, hoodie, sweatshirt); never loungewear; other known kinds of trousers or shorts are not exercise clothes | The kinds say what the clothes are made for; tops, shoes and outer layers keep the old rule by category. |
| Home and exercise suggestions add `look_for.kind`, a phrase naming kinds to look for ("joggers, sweatpants, lounge trousers or a fleece pullover", "running or training shorts") | Names the new kinds in plain words without a new gap identity; gap ids and scores are unchanged. |
| A fleece (pullover or jacket) weighs what its pile does: sherpa super heavy, polar fleece or an unsaid pile heavyweight. It sits after the owner's own words and before the tagger's weight in the order of trust | The issue asks for the weight class from the fleece; the fleece pullover is a sweater to the engine (its `app_category`), so it is a warm mid layer, not outerwear. |
| The tagger reports the kind (schema version 2, field `garment`); older answers read as `unknown`. Only `fleece_pullover`, `performance_tee`, `athletic_half_zip` and `track_jacket` among tops, and twelve sportswear and loungewear bottoms (`BOTTOM_DRAWINGS`), change the drawing; other kinds are drawn from their details | The owner's taxonomy is the source of truth for the ids (no garment or value was added to it here). The recorded drawings are byte-for-byte unchanged, but a stored side-stripe feature on a top or trousers is now drawn, so `DRAWING_VERSION` is raised to 5 (one above main's) and the demo closet regenerated. |
| On the item page the kind is offered in words, as chips (the shared `ChipGroup`), only the kinds an item of its category can be, with no drawing per choice; setting a kind the category cannot be is refused | A top can be one of dozens of kinds, and drawing each would be slow and mostly identical. Kept to one small component (`KindChoices`) for the fuller "What is it?" picker to replace. |
| Colour-blocking and contrast binding have no value in the owner's file, so they are not tagged fields: a fleece pullover with a trim colour is drawn bound in it, and with a secondary colour is drawn with yoke, sleeves and pocket in that colour | Asked the owner in #111's pull request whether to add values for them. |

| Decision | Why |
|---|---|
| Score failing days by `frequency / 7 × weather share × 8 × failure weight` | Frequency times weather is the important part. The constant 8 preserves the old score scale (eight weather cells per occasion for a full week). The original `OCCASION_WEIGHT` is used only without answers. |
| Scale thin-place base scores, basics, orphans and wear-driven extras by applicable days too | A fixed "basic winter coat" bonus must not put winter back at the top in a hot climate. Business/formal basics cannot recreate days the owner never has. |
| Keep the existing merge and ID rule (category, formality, kind) | Hidden gaps and wishes refer to those IDs. New indoor and athletic purchases have new `lounge`/`active` kinds instead of renaming an existing suggestion. |
| Prefix the original reasons with the situation, ordinary frequency words and applicable weather | Keep the analysis's named pieces and evidence, not a generic replacement. Say "now and then", "about once a week" or "most days", not fractional days. Annual weather counts describe days **here**; the per-situation API count also includes frequency. |
| Use four complete calendar years from Open-Meteo's archive, kept for 180 days | Four years smooth unusual seasons without a large download. Only coordinates, fixed query fields/dates and automatic time-zone selection are sent; no name, answers, style or closet data. The common bounded fetch uses a 6-second timeout, 1 MiB maximum and the computer's certificates. |
| Require every date, finite low/high and precipitation, and sensible ranges | A missing season must not look like a climate with no cold days. The shared `climate.archive` reader is available for future trip history too. |
| Classify at the engine's design temperature, low + 0.3 × (high − low) | Cold ≤8°C, cool <15°C, mild <24°C, hot otherwise. Wet means ≥1 mm total precipitation (including snow's water equivalent); the wet share is conditional on the band. |
| Failed archive requests reuse valid same-place data, clearly marked old, or use equal bands and equal wet/dry | A lookup failure must not stop gaps or quietly claim home weather was used. Retry at most hourly, allow seven days after year-end before requesting the new year (January 8 UTC), and discard kept weather when the place changes. A response missing only the newest year's tail keeps the previous four-year answer without a connection warning. Actual connection failures remain explicit. Cache writes check the place and reservation under the settings lock and only write changed state. |
| Taste needs at least 10 distinct item/day wears across 3 items, or 5 rated active items | Less says nothing: no taste claim or guessed preference. Each enabled evidence source contributes separately. The rules are in `taste.py`, not a model. |
| Attribute preference needs 2 positively evidenced items of the same category and at least 4 points | Colours, patterns, fits and formality are counted separately for each garment category: tee colours cannot recolour leather shoes or belts. Each wear is one point, capped at 10/item; love = 4, like = 2, meh = 0, dislike = −4. A dislike overrides historical wears. Colour compatibility is ranked before taste; a favourite loud colour cannot introduce a clash. Favoured plain patterns and fits can be suggested; the required occasion is not weakened to match taste. |
| Avoidance needs 2 negatively evidenced items of the same category, at least 75% of that category's items with the value, and negative total points | One disliked shirt does not mean every shirt with its fit or pattern is disliked. Never-worn items contribute −2 only after 180 days of ownership, a 90-day wear log with enough wears, and 90 days of the piece's own season within that log and ownership. Season exposure uses Insights' shared rule; a summer-only log says nothing negative about winter coats. Age is measured at the log's last date, not today's clock. Avoided fits/patterns are removed from suggestions and included as exclusions. |
| Confirmed `never_wear` holds back the same category and dress/kind for shared situations, except outerwear | Coats and jackets solve different weather needs and never suppress each other. Home/exercise kinds stay distinct. Other situations survive with reduced score; wishes are never silently removed. Every held-back suggestion remains listed with the hide responsible and Undo, including beyond the open-result limit. Old hides affect only themselves until the owner explicitly agrees to broader hiding. Per-closet consent and situation snapshots live in settings, matched to the database hide timestamp; no migration or destructive deletion. |
| Demo has fixed example life answers and climate shares; its questionnaire is read-only | The owner's place and answers must not change the example or send a weather request. Items, wears, hides and wishes in the demo remain independently editable as before. |
| Cache includes life/climate context and ownership dates; decisions are still applied afterwards | Answer, place and climate changes cannot serve yesterday's analysis; a wash or picture update still does not trigger a slow analysis. Undoing a hidden suggestion is immediate. |

### What the engine knows about the cloth

`closet_rows` in `backend/closet/today.py` is the one place that prepares the closet for the outfit engine and the gap analysis (`POST /api/outfits/suggest`, `POST /api/outfits/today`, `GET /api/gaps`). Each row carries the weight class and the sleeve taken from the tagger's stored answer (`tag_answer`), in the keys the engine already read (`weight_class`, `silhouette.sleeve`); `outfits.py` is unchanged.

| Decision | Why |
|---|---|
| Order of trust for the weight class: (1) what the owner set by hand, that is words in a material or name whose `source` is `user`, as `items.py` records it; (1b) for a fleece pullover or jacket, its pile (see #111 above); (2) the tagger's `details.weight` unless `unknown`, then, for knitwear, its knit gauge; (3) the words in the name and material; (4) the category. For the sleeve: (1) the silhouette's sleeve (the owner's, or the answer's copied there), (2) the answer's sleeve length, (4) the category's usual sleeve | The owner's own words are what they know about their clothes; the tagger looked at the cloth, which says more than a word in a name the owner did not choose ("Linen shirt" from the demo, a material the tagger filled in). A name typed at upload has no `source` of `user`, so it counts as words (3), not as the owner's: there is no record that it was meant as a weight. Steps 3 and 4 are the engine's own guess, unchanged. |
| A bare fibre the owner types ("wool", "cotton") does not overrule the tagger's weight | Cotton and wool come in every weight; typing "100% cotton" from a care label is not a statement that the cloth is midweight. Any more specific word (flannel, linen, fleece, merino and the rest of the engine's `WEIGHT_WORDS`) does. |
| Knit gauge to weight class: extra fine and fine are lightweight, medium is midweight, chunky is heavyweight, super chunky is super heavy (`KNIT_GAUGE_WEIGHT`) | A fine knit is worn like a shirt and goes under a jacket; a chunky one is the outer warmth of an outfit. Only used when the tagger gave no weight; it gives a gauge only for knitwear. |
| Sleeve length to sleeve: sleeveless is none, short and elbow are short, three-quarter and long are long | The engine only asks whether a top is long-sleeved (warmer, and too warm on a hot day); a three-quarter sleeve covers most of the arm. |
| A stored answer that is missing, empty, not valid JSON or not the expected shape counts as nothing known | Old items, items not described yet and a damaged row must never stop the outfits or the gaps; they keep the old guess. |
| The gap analysis's cache is keyed on the rows as the engine reads them, which carry the weight and sleeve taken from the answer, not the whole answer | A new answer that changes an item's weight gives a new analysis; one that changes only details the engine does not read (buttons, pockets) keeps the cached one. |

### Worn outfits and learning from ratings

Storage in `backend/closet/worn.py` (migration 0010), the learning in `backend/closet/outfits.py` ("learning from ratings"; every number a named constant at the top), the screens in `frontend/src/screens/Worn.tsx` and the question on Today.

| Decision | Why |
|---|---|
| A worn outfit is its own record next to the wear log, with the pieces by place, the day it was offered for, and the score and sentences it was offered with; each piece remembers whether recording the outfit added its wear | The wear log stays the one record of wears. Removing an outfit then removes only the wears it added, never one recorded on its own. |
| The same pieces recorded again on the same day give back the outfit already there | "I'm wearing this" on the computer and then on the phone is one outfit worn, not two. Two outfits that day with different pieces stay two (a change of clothes). |
| Removing an outfit hands a wear it added on to another outfit that day holding the same piece, instead of keeping it unowned | So removing the two in either order leaves the wear log as it was before either. |
| A deleted item stays part of the outfits it was worn in (listed as `gone`); such an outfit is still listed but no longer teaches anything; one with no piece left goes with the last one deleted | A rating is about the outfit as it was worn. Rebuilding it from the pieces left would move a "not again" onto tee, jeans and sneakers that were never rated together. An outfit with nothing left to show is not worth a row. Archived pieces are still in the closet, so they are shown as themselves, marked archived, and the outfit still teaches. |
| Sentences an outfit was offered with are cut to 30 and each to 500 characters, not refused | They are made from item names, which have no limit; recording what was worn must never fail because of them. |
| The ratings are three (loved it, fine, not again) and the reasons eight (too warm, too cold, too dressed up, too casual, colours clashed, uncomfortable, got compliments, other with a note) | Short enough to answer with one hand in the morning. "Fine" with no reason teaches nothing. |
| Loved (or "got compliments") adds 1 point for each pair of its pieces in an outfit, at most 4 | Scores are about 80 for an outfit that breaks nothing, so this decides between outfits that are otherwise about equal and never more: 4 is well below what one broken rule costs (20), so a loved outfit never beats what the day needs. |
| "Not again": that exact outfit (base, mid, outer, bottom, shoes) is never offered again; its pairs cost 3 points each, at most 9 | Pairs only, so the same pieces in other company stay welcome. Which pairs follows the reasons: none, "uncomfortable" or "other" mean every pair; "colours clashed" the coloured or patterned pieces; "too dressed up"/"too casual" the most/least formal pieces, and only on a day of the same occasion; warmth reasons say nothing about which pieces go together. An outfit holding such a pair says so in a warning. |
| When the outfits that keep the rules were all rated "not again", Today offers none and says why, with a pointer to change the rating; it does not fall back to the relaxed rules | A rating must never be the silent reason an outfit that breaks a rule is shown. Offering the refused outfit after all would ignore what the owner said; saying so plainly lets them decide. |
| "Too cold" or "too warm" on a day within 4°C of today (by the temperature the day is dressed for) moves the warmth aimed for by half a point each, at most a point and a half either way | One point is about 2°C. Bounded, so a run of cold days cannot dress the owner in a coat in summer; ratings of days unlike today do not count. Outfits recorded by hand have no day remembered, so they never move it. |
| The engine stays pure: `today.py` reads the newest 200 rated outfits and `outfits.feedback_from` turns them into what `suggest` takes | The same ratings and day always give the same outfits, and with no ratings the outfits are exactly those of the rules alone. |
| A sentence names the rating that shaped an outfit ("You loved these together on 3 November", "Dressed a little warmer than usual: you were cold on a day like this on 5 November") | The owner should see why the app changed its mind. |
| Today asks about yesterday's unrated outfit first, then today's; the question sits below the outfits and "Not now" is remembered on the device per closet | Today's outfit is still being worn in the morning; the question must never push the outfits down. |
| "Wear this again" starts Today from the outfit's pieces that can be worn today and fills the rest | A piece in the wash should not stop the outfit; the screen names what was left out. |
| The first page of worn outfits is kept on the device per closet, removed on logout with the other saved copies, and fetched again after every change; offline, rating and removing are off and say why | The service worker does not keep `/api/outfits/worn`: it keeps answers by address, so after switching closets it would show the demo closet's outfits as the owner's. Fetching again after a change keeps the copy from showing a rating already changed, or Today asking again about an outfit already rated. |

### Would this work?

The check is `backend/closet/wouldwork.py`, pure and deterministic like `gaps.py`; the checks, the photo and the routes are `backend/closet/wouldjobs.py`; the screen is `frontend/src/screens/WouldWork.tsx`, with its words in `frontend/src/wouldwork.ts`.

| Decision | Why |
|---|---|
| The piece is tried as if it were in the closet: `gaps.find_gaps` is run with it and without it, and `outfits.suggest` is asked, built around it, for each of the gap analysis's 40 kinds of day | The same engine and analysis as Today and What's missing, so the answer agrees with them and can be explained. Neither is changed; the check reads their own pieces and rules as `gaps.py` reads the engine's. The only change around them is that the app's `gap_analysis` takes the rows it has already read (`gap_inputs`), which gives the same answer as before. |
| Five verdicts, picked in this order: **Not enough in the closet to say** (fewer than 8 pieces of clothing, as the gap analysis); **Hard to wear with what you have** (below); **Fills a gap** (below); **Works, but you have it already** (at least one piece owned does the same job); otherwise **Works, and adds something** | Hard to wear comes before filling a gap: a piece that fills a gap on paper but goes with nothing does not fill it in practice. The thresholds are named constants at the top of `wouldwork.py` and were set by trying pieces on the demo closet (a rain-proof coat, a fourth pair of jeans, plaid formal trousers, a floral shirt, brown dress shoes, and the demo closet without its trousers or its coats); they may want moving once the real closet is in. |
| **Fills a gap** is judged by days, not by the gap's score: the kinds of day a gap fails on without the piece are compared with those it fails on with it. A gap is filled when it goes, or when at least half of its failing days (`FILL_MIN_SHARE`) are freed and on each of those the piece makes a good outfit or no piece of its kind does better (below). A gap that rests on no days (a kind of piece missing, pieces nothing goes with) is filled when it goes. When the analysis is run with the piece, a "thin place" that rests only on the piece itself is dropped | With the piece added, the gap analysis says that very piece is now a thin place ("only one pair of smart trousers"), so the score of "Smart trousers" barely fell even when grey business trousers were exactly what it asked for. A gap whose only remaining finding is the candidate is filled; the score would have needed a threshold that rewards no piece in particular. The same rule stops a piece from being said to fill a gap whose days it does not change (light trousers for hot days are not filled by navy business trousers, and do not rise because of them). |
| **Hard to wear** is judged only on the kinds of day that suit the piece, and only on those where an owned piece of the same kind (up to 6, `COMPARE_MAX`, most worn first) makes a good outfit and the candidate does not. It is hard to wear when it makes a good outfit on fewer than 2 of those days, or on less than a quarter of them. Days where no piece of its kind does better are the closet's shortfall: the answer says so ("…that is what the closet lacks, not this piece") and does not count them against the piece | A white polo in a closet with no sweater or jacket is short of warm on every cool day, but so is every top the owner has; blaming the polo, with a reason that was not the one found, was wrong. The sentence under the verdict is always the reason that was found. |
| Every sentence must be true of every piece or day it speaks for: "all of them" only when every one fails for that reason (otherwise "three of them…, two…"); "covering days nothing covers now" only for days on which the piece makes a good outfit; "breaks a rule" only for the piece's own failing days; when the only piece doing the same job is one rated dislike, the answer says so ("…and you rated it dislike") instead of "nothing you own does the same job" | The answer is meant to be explained and trusted; one false "all" or "nothing" undoes that. |
| "A good outfit" is one the engine makes around the piece with none of its own warnings (a clash, the wrong warmth for the day) on a day the piece itself suits (its season, and an outer or middle layer not on a hot day) | The engine can be made to put any piece in an outfit; this keeps "it works on 16 kinds of day" honest. |
| "Does the same job" is the same kind, the same formality and the same colour group: dark neutrals (black, navy) together, light ones (white, cream), earth tones (tan, brown), and otherwise the engine's colour families; jeans in any blue, navy, black or grey wash are one group | "You have three like it, and two of them are hardly worn" is the most useful sentence the check can say, so it should catch the pieces the owner would call the same; jeans are worn with the same things whatever the wash, as the engine counts blue jeans as neutral. "Hardly worn" is at most once in the log, said only when the log has at least 10 wears (as the gap analysis). |
| A gap found only from the wear log ("another one like the piece you wear most") is listed but does not make the verdict "Fills a gap" | The same piece again is always the answer to that gap, so it would call every repeat a gap filled; the pieces like it that are hardly worn are often the better answer, and the verdict says "you have it already" with them named. |

Restoring an older backup forgets the requests made after it, so that month can read lower than Anthropic's bill. Plan requests are recorded with their tokens but cost 0: nothing is charged per request on a plan. |

| When Claude Code's sign-in is refused ("Not a valid API key for this workspace", "Invalid API key", not logged in) the item waits and says why, instead of using up its three tries | Found on the owner's first item in 0.2.0: Claude Code was using an API key Anthropic refused, Closet read the refusal as a bad answer for that photo, and after three tries said to retake the photo. Facts checked in Anthropic's documentation on 2026-11-12:
- Windows install needs no Node.js: `irm https://claude.ai/install.ps1 | iex` in PowerShell, or `winget install Anthropic.ClaudeCode`. The program lands in `%USERPROFILE%\.local\bin\claude.exe`; the app looks there as well as on PATH.
- Signing in once with `claude` persists (stored in `%USERPROFILE%\.claude\.credentials.json`); later `claude -p` calls from another program use it. `claude auth status` exits 0 when signed in.
- The support pages say `claude -p` under a plan login draws on the plan's limits. The legal page restricts third-party developers offering Claude login to their users, and says this does not prevent an end user signing in to the unmodified Claude Code program with their own plan. A personal program calling that program on the owner's own machine appears to be inside those terms, but the docs do not say so in as many words, and Anthropic reserves the right to change enforcement.
- When a limit is hit the message reads "You've hit your session limit · resets …" (or weekly). The exit code for that case is not documented; the app matches on the message.

The shade is always a darker tone of the cloth: a lighter one on dark cloth looked like gloss. The outline is only slightly bolder than a midweight one. Tried and dropped: showing the cloth's underside below the hem and cuffs, which read as a thicker outline. Light cloth has no positive sign of its own yet (drape wrinkles are the idea). |

The owner's chest is about 39 inches, which is the size the measurements already assume (a medium: a shirt 56 cm across the chest laid flat). |
| Anchor points are points on the wearer, not on the garment | Neck base and the shoulders of a 46 cm frame, the same for every top. How far the cloth extends beyond them is the fit. |
| Tailored jackets have their own construction | A blazer drawn as a shirt body with lapels was rejected as narrow and wrong. Built by a Copilot agent (#12) in its own function, so no other drawing changed; a test holds a fingerprint of every other drawing and fails if one changes by accident (when a drawing is changed on purpose, its fingerprint is recorded again in the same change). Jackets use the same 84% share of their flat width as every other top, so a jacket and the shirt under it stay in proportion. |
| Jacket details read the way a tailor counts them | Fixes to the faults left in the tailored jacket (#109). A double-breasted jacket tagged with one or two buttons is read as the buttons that fasten, so it is drawn as the usual 6x1 or 6x2 (six buttons in three rows; on a 6x1 the lapels roll to the bottom row); tagged with more, that is every button on it. A single-breasted jacket tagged with three buttons is a three-roll-two: two buttons below the lapel and the top buttonhole showing on the lapel's roll, its button hidden. A jacket's buttons are drawn at least 3:1 in contrast against the cloth (the level the web accessibility guidelines set for large shapes), lightened or darkened as little as needed; on black or navy, where a darker shade would not show, the jacket's inside is drawn lighter than the cloth instead. Sleeves hang at most 19 degrees from the side with a rounded underarm, so the two outlines do not run into a dark wedge; lapels broaden with a fuller fit (0.4 cm for each cm of chest it adds). |

The front that lies on top (the wearer's left, as on men's clothes) carries the buttonholes, vertical on a shirt or cardigan and horizontal on a jacket or coat; the one underneath carries the buttons. Each front swings open about its side seam like a door, so it is drawn narrower, as a turned panel looks, while sleeves and sides stay put: the garment keeps its width and its shoulder points, and a double-breasted coat opens as far as a shirt. The inside of the back shows between the fronts and inside the neck. Each garment only states where its top front's edge runs; the renderer does the rest, so every garment that opens gets this. Open or closed is a choice made when wearing, not a tag on the item. |
| Reference drawings may be downloaded from Wikimedia Commons, Openclipart and SVG Repo | Added to the `daily-clother` environment at the owner's prompting. They are looked at and measured, never copied into the repo. Commons rate-limits hard: one request, then wait. |

### The outfit as worn

`backend/closet/drawing/figure.py` (`figure`, `plan`), served by `POST /api/outfits/figure`. It only places and stacks the existing item drawings.

| Decision | Why |
|---|---|
| One front-view figure, no body drawn: the clothes stand as on an invisible mannequin | A body would need skin tones and a face, and says nothing about the clothes. |
| Each piece is drawn from exactly what its own item drawing is drawn from (`illustrations.describe`): the tagger's answer with the owner's corrections, else the category and fields, in the item's colour | The figure must show the same garment as the closet. Patterns and photo tiles are not used (solid colour), so the figure is the same whether or not the photo is there. |
| Every top is placed by the shared neck and shoulder anchors, unmoved and unscaled; the tops are drawn 24 px lower than on their own card | The anchors are points on the wearer, so tops line up by construction. The drop leaves room above for a hood, inside the area the depth shading covers. |
| A mid or outer layer is worn open when its front opens all the way down (buttons, French placket, hidden placket, double-breasted, zip) and the template can open it; otherwise closed. The base top is always closed | That is how they are worn: a jacket, overshirt or cardigan open over what is under it; a pullover, hoodie or polo over a tee cannot be. Open uses the existing `layer` order (the outer garment's inside back, the whole garment underneath, the fronts and sleeves). Three layers nest the same way, from the inside out. |
| A closed layer shows only what would really show of what is under it: inside its own outline nothing; above its neckline a band as wide as a collar; below its hem as wide as its body; and through its own neck opening (a shirt collar in a V-neck) | A shirt collar above a crew neck and a shirt hem below a short sweater show; a tee's sleeves do not poke through a sweater's. When a layer underneath has longer sleeves (a long-sleeved shirt under a short-sleeved overshirt or a vest) nothing of it is hidden, so its sleeves show. |
| The waist (where a mid-rise waistband sits) is 48 cm below the base of the neck; the trousers' waist anchor is put there | 48 cm on a man of about 178 cm with a 46 cm shoulder frame. It is above the hem of every top the templates draw (a cropped top ends about 60 cm below the neck), so a top always hangs over the waistband: tops are not tucked in. |
| One scale for every piece: 3.3 px per cm, the tops' own. Trousers (drawn at 3.92 px per cm) are scaled by 3.3 / 3.92; a shoe (320 px long on its card) by 29.5 cm × 3.3 / 320 | The tops' scale is the one the anchors are measured in, so tops are never resampled. A 76 cm shirt and trousers with a 32-inch leg are then in their true proportion. |
| Trousers are drawn at the same 84% of their flat width as tops; their lengths stay true | They wrap round the legs as a top wraps round the body. At their full flat width their hips stood out past the hem of every top. This is a choice someone could make differently: "keep their own proportions" could mean the full flat width. |
| The ground is the waist plus a 27 cm rise, an 81 cm inseam and 5 cm; every pair of shoes stands on it, whatever the bottom | Full-length trousers then break on the shoe. Shorts and cropped trousers end where they end, and the shoes stay on the ground under the invisible legs, so the figure keeps its height and shorts look short. |
| A pair of shoes is the side-view template twice, mirrored, toes out, heels 5 cm either side of the centre, squeezed to 70% of its length | The template draws one shoe from the side; a fashion flat shows a front-view figure's shoes as two side views turned out. Squeezing them reads as turned partly toward the viewer and keeps them under the trouser hems. |
| Back to front: shoes, trousers, then the tops from the inside out | Trouser hems fall over the shoes; tops hang over the waistband. |
| The figure has its own canvas: everything drawn, plus 18 px on every side | A knee-length coat, shorts or boots each change the outline, so no fixed card fits all. The Today screen scales it to fit. |
| It never fails: a missing place is not drawn; an item in the wrong place (shoes as the bottom) is skipped; a piece that cannot be drawn from its description is drawn as the plainest of its category; if nothing can be drawn, an empty card | An outfit with one odd item should still be shown. |
| A sheet of figures from the demo closet is kept at `docs/screenshots/outfit-figures.png` (and `.svg`), written by `tools/make_figure_sheet.py` | So a change to the figure can be judged by looking, as the issue asked. |
| The kind of shoe (a footwear id such as `tassel_loafer` or `cap_toe_oxford`, or a footwear word such as `wingtip`, `open_derby` or "5 eyelets") comes from the words the tagger writes in `other_features`, read by `taxonomy.shoe_words`; no schema field was added. A footwear id sets the shoe style (a brogue keeps a tagged derby lacing, otherwise oxford); its details refine it. Defaults: a loafer has a penny strap, a sandal two straps, a dress shoe five eyelets. Words the drawing shows leave the item's "seen but not drawn" list | The issue asked for no schema change, and a schema change makes every stored answer stale. The taxonomy's 47 footwear ids are listed in `COVERAGE` as drawn, approximate (drawn as the closest shape, the note says which) or not drawn. |
| Accessories are placed by the point their template is drawn about: a belt round the trousers' waistband, the first top then tucked in under it (and under any layer worn over it); a scarf at the neck point, over every top; a hat above the neck point, where a forehead would be; a bag beside the figure on the viewer's right, its handle at the height of a hand. One of each is drawn, the first given; ties, gloves, socks and the other accessories are not drawn on the figure | A belt over an untucked top would hide it; a belt is worn to be seen. With no body drawn, a hat floats where the head would be. The sizes and heights were chosen by eye from the sheet `docs/screenshots/accessories.png` (written by `tools/make_accessory_sheet.py`), and someone could reasonably choose them differently. |

## Patterns drawn from the photo

The owner's original spec asked for patterns to come from the photo; it fell out when the drawing moved into
the app (issue #37 said the app must not need OpenCV) and was never decided against. Rebuilt and tested on the
owner's own and other real photos (bench/experiments/patterns, with notes there).

| Decision | Why |
|---|---|
| OpenCV is part of the app (`opencv-python-headless`), used only by `closet/patterns` and the cutout's see-through check; the drawing code still never imports it | The owner chose quality over the program's size. A numpy/Pillow port was built and matched OpenCV, but the methods that mattered (template matching, k-means, image quilting) are better kept on the library the bench uses. |
| A plaid is flattened, not sampled: its repeat is found over the whole garment, every area matched against it to a tenth of a pixel, the crumpled cloth mapped back into one straight repeat (each front on its own when they agree), and that repeat drawn | Every square cut from a photo carried its folds, a pocket or the button strip, and mirrored squares made kaleidoscopes. Redrawing the plaid as flat bands lost the thin white lines. |
| A plaid with no regular repeat (madras) is measured whole and kept as one garment-sized tile | Quilting broke a plaid's lines. |
| Stripes are measured as a sequence across the whole garment: regular stripes folded onto one sharp repeat (each area matched to the whole repeat), placed bands (a polo's chest band) drawn over a crisp ground; the collar is cut from the ground, and the sleeves too unless the photo shows the bands on them | A polo's band landed on its collar and sleeves; rugby shirts carry their bands onto the sleeves, so it is measured, not assumed. |
| Colours of stripes are corrected from Claude's colour words: when it says the item has white or cream, the lightest neutral yarn is made that colour and every yarn moves with it (brightness freely, balance by at most 8%) | Most photos are taken in tinted light; a white shirt measured grey. |
| Florals, camouflage and other prints are pieced (image quilting) from big squares from all over the garment, after turning it upright and evening out the light | One repeated square showed rows of the same flower; a slanted shirt gave slanted streaks. |
| Placing a plaid: Claude gives the buttons, neck, hem, shoulders and underarms (`tagger/landmarks.py`, the larger model); each front is placed by matching the photo beside the button line against the repeat, held out against cloth lower down | Finding buttons in the image alone took pocket edges and round shapes in a plaid for buttons; the tagging model put underarms on the chest. Placing through the flattening map alone was right on one front only. |
| Measuring runs in the background after an item is described (`patjobs.py`), and again when the owner changes its pattern; a failure leaves the item drawn in its colour with a note | It takes from a second to two minutes; no item waits for it to be usable. |
| The second background model (u2net) is downloaded after the first and asked as well when a cutout is more than 20% see-through inside its outline | The first model takes a plaid's dark checks for background (22% of the owner's shirt kept); the two combined kept 66%. Six plain or striped test shirts were left exactly as they were. |
| The kept pattern is JSON in `items.pattern_fill` (migration 0013), a tile as a small WebP inside it | One row holds the item; backups and restores carry it with no new folder. |
| A graphic on a top (a logo, a chest print) is lifted from the cutout (`fills.extract_graphic`, the bench's own) and kept in `items.pattern_fill` as an optional `graphic` part: a WebP with its transparency and its box in fractions of the garment, drawn over the cloth in its colour; no new migration, and the kept format stays version 1 because data without the part reads as before | The issue asked for no schema change if `pattern_fill` could hold it. Fractions of the garment (not of the padded cutout) put the print in the same place on the drawing's outline. |
| A print is lifted when the item is a top and its pattern is `graphic`, or `other` with the pattern name `novelty`; Claude is not asked for landmarks for it | The tagging schema does not yet ask for the taxonomy's `graphic_technique` and `graphic_placement` (adding them would change the schema version and every stored answer's shape), and the coarse pattern already says graphic. A print is placed by its own box, so landmarks would only cost a call. Shoes, trousers and accessories are left plain (sneaker logos are parked). |
| A measured pattern's colours come from its stripe band widths, or from its tile's pixel area reduced to 16 colours; a colour lying between two or three others (within ΔE 10) is a crossing of those yarns and its area goes back to them (`palette.py`, numpy and Pillow only) | Without that step a navy and green plaid also reported the teal where they cross. Colours under 4% are dropped and at most four kept (the main colour and three others). |
| Each measured colour gets the nearest colour word (the drawn shade plus two more shades per word); Claude's word is kept when it is at most ΔE 12 further away | Claude's words stay where the photo agrees with them; the limits are starting values to tune on the owner's photos. |
| The item's main colour becomes the largest measured colour unless Claude's main colour covers at least ¾ as much, and its shade becomes the measured one; both stay the tagger's (confidence 0.9) and a colour or shade the owner set is never changed | The outfit engine and What's missing read `color` as before, so matching improves with no change there. The measured colour is part of Claude's side like the drawing, not an entry in the history; it is laid over again after describing again or undoing. |
| The measured colours are kept inside `items.pattern_fill` with the pattern they were measured for, and used only while the item still has that pattern; the item page shows them as swatches beside the pattern word | No schema change. Items measured before this are not measured again for it: they get colours the next time they are described or their pattern changes. |

## Trip packing

- **Usual weather from five years.** Trip days inside Open-Meteo's 16-day forecast use the forecast; later days use the same calendar days in each of the last five years from Open-Meteo's archive, averaged, and a day counts as rainy when it rained in at least half of those years (`backend/closet/tripweather.py`). Each day says which it is ("Forecast" / "Usually, on these dates"). If the archive cannot be reached, those days say the weather is not known and the forecast days still answer.
- **Re-wear rules** are named constants in `backend/closet/trips.py` (`REWEAR_DAYS`: tees 1 day, shirts and polos 2, hoodies 3, sweaters and trousers 4, jeans 5, shorts 3; one coat or jacket; at most two pairs of shoes unless the days cannot be covered otherwise). "I can wash there" multiplies them by `WASH_FACTOR` (2).
- **Basics** are counts, not closet items: underwear and socks one per day plus one spare (fewer when washing), sleepwear, and an umbrella when a rainy day has no rain-friendly coat.
- **The planner** dresses the hardest days first, preferring pieces already packed, then fewest new pieces, then the engine's score. It calls the outfit engine's own helpers; `outfits.py` itself is unchanged.
- **Where Trips sits.** In the sidebar on the computer. The phone's bottom bar is full, so there is no tab: a "Trips" link sits on Today's header and in Settings under "Where you are".
- **Migration number.** `0012_trips.sql`: migrations `0010` and `0011` are assigned to branches merging before trips; a migration must be above the closet's current version to run.
- **A replan keeps the saved weather for days a refresh cannot answer.** It says the weather could not be refreshed and does not lose a usable plan just because the weather service is down.
- **Usual-weather answers are keyed by the exact days requested, and use only past calendar matches.** If the target day is more than a year ahead, the nearest matching date can still be in the future; the archive only has dates already passed. February 29 uses February 28 in years without a leap day.
- A saved trip keeps the weather its plan was made for; opening it checks the forecast again and only offers "Plan again" when it changed.

## The design system

- **Type scale, ratio 1.25 from 16px:** 12 / 14 / 16 / 20 / 25 / 31 px (`--text-xs` to `--text-2xl`), weights 400 body, 560 labels, 650 headings. Headings of 25px and up are tightened by -0.015em and balanced over their lines. The app had about 30 sizes; `frontend/src/design.test.ts` fails on any `font-size` off the scale, a radius that is not a token, or a colour outside the token blocks (garment swatches live in `labels.ts`).
- **Spacing on a 4px base:** `--space-1` to `--space-8` = 4, 8, 12, 16, 20, 24, 32, 48. Defined now; existing paddings move onto them in the later design issues that change layout.
- **Radii:** 8 (inputs, small tiles), 14 (cards), 20 (dialogs and sheets), pill (chips, buttons).
- **Colours:** four text levels (`--ink`, `--ink-2`, `--ink-3`, `--ink-4`), four surfaces (`--bg`, `--surface`, `--surface-raised`, `--inset`) and borders as see-through ink (`--line-soft`, `--line`, `--line-strong`), so they suit any surface. Dark mode keeps each hue and only changes lightness. Item tiles stay light in dark mode.
- **Depth:** cards have a soft ring plus a small shadow in light mode; in dark mode only a 1px see-through ring, because shadows do not show on a dark canvas.
- **Primary button in dark mode** is light green `#8fb5a5` with dark text (about 7.5:1); the old `#4d6a5f` with light text was too weak.
- **Disabled** is a flat inset fill, a dashed edge and the faintest text, not lowered opacity, so it reads as off rather than faded. Pressed buttons shrink to 97% over 120ms, except when the device asks for reduced motion.
- **Light or dark:** `<html data-theme="light|dark">` wins over the device; with no attribute the device's setting is followed. The choice is kept in this browser's `localStorage` (`closet.theme`), not on the server, since it is about the device; "Same as this device" removes it. It is applied as the app's script starts, so a forced choice can show the device's colours for a moment while the page loads, and the browser bar colour still follows the device.
- **Shared pieces** (`frontend/src/components/ui/`) style themselves with `:where()`, which has no specificity, so a screen's own class can still set size and padding without fighting them.
- **Phone or wider** is decided by one media query, `PHONE` in `components/ui/Sheet.tsx` (699px wide and below; a tablet gets the popover even though it still has the tab bar). `Sheet` is the one way to show choices that do not fit in place: on a phone a sheet from the bottom with a dim backdrop, on a computer a popover under its button or the choices opened in place. Escape and "Done" close it.
- **Closet filters live behind one Filter button**, In use / Archived included, so the phone shows clothes in the first screen; the filters that are on stay visible as chips that remove themselves when tapped. Search and the Photos / Drawings switch stay in the toolbar because they are used most.
- **The item page reads first and edits on demand.** Every detail is a label / value row; tapping it opens that detail's chips. On a phone the sheet closes after a choice (one tap to open, one to choose); on a computer the chips stay open in place, so several changes can be tried in a row. "How you feel about it" stays open after a choice on both, because it has a "Why?" box to fill.
- **On a computer the item panel scrolls with the page** instead of in a box of its own, 420px wide, and only exists while an item is chosen. It opens level with the top of the screen even when the grid has been scrolled, so a tile far down does not open a panel out of sight.
- **The model banner shows only while it needs something done** (not set up, or the download failed), not while downloading and not offline. Hiding it lasts until the browser tab is closed, and only for the state it was hidden in, so a new failure shows again.
- **Page widths:** a page that is one column (Add, Settings, Review, Trips, Worn) is at most 720px wide (`--content-w`) and starts beside the sidebar, not centred; a page with two panes (Closet, What's missing) uses the full width. A trip's packing list and its days now stack in that column, and the Review card's picture is narrower (17rem) beside its fields.
